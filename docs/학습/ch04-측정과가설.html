Chapter 4

측정: Opus만큼인가 + 왜 이렇게 됐나(가설)

"좋아진 것 같다"는 측정이 아니다 — 같은 자로 재고, 결과를 가설로 설명하고, 한계를 정직하게 적는다.

1. 왜 측정이 핵심인가

로컬 4B 모델(Gemma)이 클라우드 최고급 모델(Claude Opus)만큼 magicJar 도메인 질문에 답할 수 있을까? 직감으로는 절대 알 수 없다. 필요한 것은 공정하고 반복 가능한 자(尺)다.

핵심 원칙

같은 30개 질문 세트를 매번 고정해서 쓴다. 질문이 바뀌면 점수가 바뀐 게 모델 때문인지 질문 때문인지 알 수 없다. 30 고정 질문 = 불변의 자. 이 자로 Phase 1 → Phase 2 → Phase 3을 일관되게 비교한다.

숫자가 있어야 비로소 방향이 생긴다. "Gemma에 RAG를 붙였더니 답이 좋아진 것 같다"는 인상이 아니라, "Opus-judge 기준 평균 점수가 3.0 → 3.8로 올랐고, 승률이 0% → 30%로 개선됐다"는 문장을 써야 Phase 2 실험의 성공 기준을 정할 수 있고, Phase 3 증류의 학습 데이터 품질도 점검할 수 있다.

비유

마라톤 훈련을 할 때 "오늘 더 빨리 달린 것 같다"고 기억에만 의존하지 않는다. 스톱워치로 매번 같은 코스를 재야 훈련이 효과가 있는지 확인할 수 있다. 30 고정 질문 평가 세트가 바로 그 스톱워치다.

2. 측정 설계 — 4단계 파이프라인

우리의 평가 파이프라인은 네 단계로 이루어진다.

30개 고정 질문 (DSL + 시스템)
매 평가 회차 동일하게 사용. 변경 시 버전 태그 필수.
↓ Step 1
Gemma + RAG 답변 생성
로컬 Gemma 4B 모델이 RAG 파이프라인을 통해 각 질문에 답변. 응답시간(latency_ms)도 기록.
↓ Step 2
Opus 정답지 생성
로컬 claude CLI로 같은 질문 + 같은 컨텍스트를 Opus에게 전달. 이게 "기준 답안"이 된다.
↓ Step 3
Ragas 지표 측정
Faithfulness / Answer Relevancy / Context Precision — 각각 검색된 근거, 질문 관련성, 청크 정밀도를 수치화. (현재 Phase 1은 의존성 버그로 NaN — 아래 한계 섹션 참조)
↓ Step 4
Opus-as-judge 심판
Opus에게 Gemma 답과 Opus 정답지를 동시에 보여주고 우열을 가리게 함. winner (gemma / opus / tie) + gemma_score (1~5점) 반환.
↓
results.csv / results.md 저장
회차별로 보관. 점수 추이를 시계열로 비교 가능.

왜 정답지를 Opus로 만드나?

이유는 두 가지다.

  1. 지금 당장: 평가의 기준이 필요하다. 사람이 30개 질문을 매번 직접 채점하면 시간이 너무 많이 든다. Opus는 magicJar 코드를 코드 청크 기반으로 정확히 읽고, 충분히 신뢰할 수 있는 기술 답변을 생성한다.
  2. Phase 3을 위해: Opus 정답지는 나중에 Gemma를 파인튜닝할 때 학습 데이터(teacher signal)로 재활용된다. 지금 품질 좋은 정답지를 쌓아두는 것이 Phase 3 증류의 기반이 된다.
설계 패턴

평가 데이터와 훈련 데이터를 동시에 만든다. 같은 (질문, Opus답) 쌍이 평가 기준도 되고 나중에 학습 샘플도 된다. 두 번 일하지 않는다는 점에서 매우 경제적인 설계다.

3. LLM-as-judge 란

사람 대신 LLM이 두 답변을 비교해서 채점하는 방식이다. 평가자(judge)에게 질문, Gemma 답, Opus 답, 평가 기준을 프롬프트로 전달하면 judge가 어느 쪽이 더 낫고 Gemma 답의 점수가 얼마인지 돌려준다.

장점 단점 / 주의사항
빠르다 — 사람 채점 없이 수십~수백 개 질문을 자동화할 수 있음 judge 자신의 스타일·어투를 선호하는 자기편향(self-bias)이 있을 수 있음
확장 가능 — 질문 수를 늘려도 비용/시간이 선형적으로만 증가 judge가 약하면 판정 자체가 신뢰할 수 없음 (이 프로젝트에서 judge = Opus이므로 상대적으로 안전)
일관성 — 같은 프롬프트 템플릿이면 매번 비슷한 기준으로 채점 judge가 긴 답변을 무조건 선호하거나, 형식(마크다운 등)에 과하게 반응할 수 있음
정성 피드백 추출 가능 — 왜 Opus가 나은지 이유를 텍스트로 받을 수도 있음 정답이 불분명한 질문에서는 judge도 틀릴 수 있음

우리 구현의 출력

winner 필드

gemma / opus / tie 중 하나. Gemma가 더 낫거나 동등하면 gemma 또는 tie를 목표로 한다. Phase 1 smoke 결과: 2문항 모두 opus.

gemma_score 필드

1~5 정수. Opus 정답 대비 Gemma 답의 절대 품질. 5 = Opus와 동급, 1 = 거의 도움 안 됨. Phase 1 smoke 결과: 2문항 모두 3점.

4. Ragas란

Ragas는 RAG 파이프라인을 평가하기 위한 오픈소스 프레임워크다. 단순히 "답이 맞나"를 보는 게 아니라, RAG의 각 부품이 제대로 일하는지를 분해해서 측정한다.

지표 무엇을 재나 간단한 설명
Faithfulness 답변이 검색된 청크에 근거하는가 모델이 제공받은 컨텍스트 밖의 내용을 지어내지 않는지 측정. 높을수록 "할루시네이션이 없음".
Answer Relevancy 답변이 질문에 관련이 있는가 질문을 역생성해서 원래 질문과 얼마나 비슷한지 코사인 유사도로 측정. 엉뚱한 답변을 잡아낸다.
Context Precision 검색된 청크가 정말 필요한 청크인가 상위 k개 청크 중 실제로 답변에 기여한 청크의 비율. 노이즈가 많은 청크를 줄이면 올라간다.
왜 세 지표가 모두 필요한가

세 지표는 서로 다른 실패 모드를 잡는다. Faithfulness가 낮으면 "모델이 마음대로 지어냈다", Answer Relevancy가 낮으면 "엉뚱한 답을 했다", Context Precision이 낮으면 "검색이 불필요한 청크를 너무 많이 가져왔다". 하나만 봐서는 어디가 문제인지 알 수 없다.

Phase 1 현황 — Ragas 지표는 현재 NaN

ragas==0.4.3가 현재 의존성 환경에서 langchain_community 내부의 VertexAI 임포트를 시도하다 실패한다. 이 버그로 인해 run_eval이 try/except로 강등되어 Ragas 블록 자체를 건너뛴다. 러너는 완주했지만 세 지표 모두 NaN. Phase 1에서 실측 신호는 Opus-as-judge 점수뿐이다. Ragas 수치 복구는 Phase 2 의존성 업그레이드 작업으로 예정되어 있다.

5. 실제 결과 — 스모크 이밸

스모크 이밸(smoke eval)은 전체 30문항 중 2문항(limit=2)만 빠르게 돌려보는 제한 실행이다. 파이프라인이 end-to-end로 돌아가는지 확인하는 것이 목적이다.

실측 결과 요약

q01 · q02 모두 winner = opus, gemma_score = 3 (5점 만점). Ragas 3지표(faithfulness, answer_relevancy, context_precision)는 모두 NaN. 평균 응답 지연: 43,505ms (약 43초). 로컬 CPU 추론임을 감안해야 한다.

## 한눈에 보는 흐름
HTTP 요청 → 컨트롤러 → 서비스(discover)
   → 이전 상태 조회(KEPT/DISMISSED)
   → [캐시 충분하면 AI 건너뜀]
   → 프롬프트 빌드 → AI 텍스트 클라이언트 호출
   → JSON 파싱 → 종목(instrument) 매칭 → 검증
   → 캔들 가용성 보강 → 경고 생성 → 상태 저장 → 응답

두 답변을 비교해 보면, Gemma는 순서 목록으로 전체 흐름을 설명했지만 Opus는 캐시 분기(캐시 충분하면 AI 건너뜀)나 상태 조회 선행(KEPT/DISMISSED) 같은 세부 흐름까지 코드 구조를 그대로 반영했다. 점수 3과 opus 승의 차이가 여기서 온다.

6. 정직한 한계

한계 1 — Ragas 3지표가 현재 NaN

원인: ragas==0.4.3가 langchain_community 내부에서 Google VertexAI 임포트를 시도하다 실패한다. eval 러너는 try/except로 이 블록을 우아하게 건너뛰어 완주하지만, faithfulness / answer_relevancy / context_precision 세 지표는 모두 NaN으로 남는다.

결과: Phase 1에서 "검색 품질"을 수치로 직접 볼 수 없다. Opus-as-judge 점수만이 유일한 실측 신호다. Ragas 지표를 살리려면 ragas 버전 업그레이드 또는 langchain 의존성 정리가 필요하다 — Phase 2 작업 목록에 올라가 있다.

한계 2 — 임베딩 max_length=512 절단

현재 임베딩 모델이 512 토큰 이상의 청크를 조용히 잘라낸다. magicJar 코드베이스에는 500줄이 넘는 Service/Controller 파일이 여럿 있다. 청크가 512 토큰 경계에서 잘리면 함수의 후반부나 중요한 리턴값 정의가 임베딩에 포함되지 않는다. 결과적으로 검색된 청크가 불완전하고, RAG 답변의 completeness가 떨어진다.

한계 3 — 프롬프트 인젝션 미하드닝

현재 평가 코퍼스는 magicJar 자체 코드와 문서로만 구성된 신뢰 코퍼스다. 외부 사용자 입력이 코퍼스에 섞이지 않기 때문에 Phase 1에서는 이 위험을 허용했다. 하지만 나중에 사용자 자유 텍스트(전략 이름, 메모 등)가 인덱싱 대상에 포함된다면 인젝션 방어 로직이 반드시 필요하다.

한계 4 — Ragas judge 모델이 Gemma 4B

이상적으로는 Ragas 지표 계산에도 능력 있는 모델이 judge로 참여해야 한다. 로컬 환경에서 Ragas가 Gemma 4B를 judge로 쓰게 설정되어 있다면, Ragas 점수 자체가 약한 모델의 판정이 되어 신뢰도가 낮아진다. Phase 2에서 Ragas를 부활시킬 때 judge 모델 설정도 함께 점검해야 한다.

7. 가설 — 왜 이런 결과가 나왔나

숫자를 얻었으면 그 다음은 설명이다. 가설이란 "이렇게 됐을 것이다"는 추론이며, 다음 실험으로 검증한다.

가설 A — 왜 Opus가 이겼나

Gemma 4B는 파라미터 수와 사전학습 데이터 범위에서 Opus와 비교할 수 없다. 특히 magicJar 도메인처럼 한국어 + 금융 + Kotlin 코드 + 커스텀 DSL이 복합된 전문 영역에서는, 일반적인 코드 이해 능력 외에 도메인 어휘와 시스템 구조를 동시에 종합하는 추론이 필요하다. Gemma는 RAG가 제공한 코드 청크는 읽었지만, 청크 간 연결 고리(예: KEPT/DISMISSED 상태가 캐시 분기에 미치는 영향)를 스스로 이어 붙이지 못했을 가능성이 높다.

다음 실험: RAG 청크 수(top-k)를 늘렸을 때 Gemma 점수가 오르는지 확인.

가설 B — 왜 gemma_score가 3(중간)인가

완전히 틀리지 않은 이유는 RAG 덕분이다. Gemma가 스스로 magicJar 아키텍처를 알 리 없지만, RAG가 관련 코드 청크를 제공했기 때문에 최소한 "어떤 서비스가 있고 어떤 단계를 거친다"는 구조는 파악할 수 있었다. 그러나 3점에서 멈춘 이유는 청크 제공 = 완전한 이해가 아니기 때문이다. Opus는 같은 청크를 받고도 메서드 의존성, 예외 경로, 설계 의도까지 종합했다.

다음 실험: RAG 없이 같은 질문을 Gemma에게 던졌을 때 점수가 몇 점인지 비교.

가설 C — RAG가 없었다면 점수가 더 낮았을 것이다

magicJar는 공개 데이터셋에 없는 커스텀 코드베이스다. RAG 없이는 Gemma가 StrategyResearchAiDiscoveryService나 StrategyResearchAiTextClient의 존재조차 알지 못한다. RAG가 관련 청크를 제공하지 않았다면 답변은 "그런 정보를 모릅니다" 또는 다른 프레임워크의 패턴을 억측하는 수준이었을 것이다. 점수 1~2 예상.

실험 제안: RAG on/off A/B 테스트. 같은 30문항을 RAG 없이 Gemma에게 돌려서 점수 차이를 직접 측정.

가설 D — 512 절단이 점수를 낮추고 있다

q01의 컨텍스트에는 StrategyResearchController.kt(270줄)가 포함되었는데, 이 파일은 임베딩 단계에서 512 토큰 경계에서 잘렸을 가능성이 높다. 잘린 청크에서는 컨트롤러 후반부 엔드포인트(core-prompt 수정, 프리셋 추천 등)가 Gemma에게 전달되지 않았을 수 있다. 결과적으로 Gemma의 답변에서 전체 흐름 중 일부가 누락된 이유가 여기에 있을 수 있다.

실험 제안: max_length=1024로 늘리거나 청킹 전략을 함수 경계 기반으로 변경 후 점수 재측정.

8. 다음 단계 — 무엇을 측정하면 좋은가

Phase 1에서 얻은 숫자를 바탕으로 Phase 2에서 시도할 실험들이 자연스럽게 도출된다.

실험 목적 기대 신호
RAG on vs off A/B RAG의 기여도 직접 측정 RAG off → 점수 1~2, on → 점수 3 확인 시 가설 C 검증
top-k 변화 (3 → 5 → 10) 더 많은 청크가 답변 품질을 올리는지 확인 3 → 5일 때 gemma_score 개선 여부
청킹 전략 변경 (고정 크기 → 함수 경계) 512 절단 문제 해소 context_precision 상승, score 3→4 가능성
Ragas 의존성 수정 후 재실행 faithfulness / answer_relevancy / context_precision 실측 NaN → 실수 지표, 검색 품질 진단 가능
Gemma 7B 또는 파인튜닝 모델 교체 Phase 3 증류 효과 검증 score 3 → 4~5 목표

Phase 3 증류로 가는 길

지금 쌓이는 (질문, Opus 정답지, Gemma 오답) 세 쌍이 Phase 3의 원료다. Opus 정답지로 Gemma를 파인튜닝하면, 처음부터 도메인 지식 없이 시작했던 Gemma가 magicJar 코드베이스에 특화된 응답 패턴을 익히게 된다. 이 과정을 지식 증류(knowledge distillation)라 부른다. 큰 선생(Opus)의 답변 스타일을 작은 학생(Gemma)에게 전이하는 것이다.

Phase 3 목표

파인튜닝된 Gemma의 평균 gemma_score가 4.0 이상이 되는 것. 그리고 winner=gemma 또는 tie 비율이 50% 이상이 되는 것. 그 시점에서 로컬 SLM이 Opus 수준의 magicJar 도메인 전문성을 갖췄다고 말할 수 있다.

이 책에 쌓일 다음 챕터 예고

5장 (Phase 2 예정): Ragas 의존성 복구 + 청킹 전략 개선 + RAG on/off 비교 실험. 숫자가 달라지면 가설 중 무엇이 틀렸는지도 솔직하게 기록한다.

6장 (Phase 3 예정): Opus 정답지를 이용한 Gemma 파인튜닝(LoRA/QLoRA). "작은 모델이 큰 선생을 따라잡는다"는 실험의 전 과정을 담는다.

이 챕터가 가르쳐준 것: 측정 없이는 발전도 없다. 지금의 NaN과 3점은 부끄러운 결과가 아니라 출발선이 어딘지를 정확하게 아는 것이다.
