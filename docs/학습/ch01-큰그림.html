Chapter 1

큰 그림: SLM·RAG·증류, 그리고 이 랩의 목표

왜 이걸 만드는가 — 작은 로컬 모델이 큰 LLM 없이도 우리 도메인을 잘 답하게 만드는 여정의 출발점.

1. 이 책은 무엇인가

이 책은 magicJar SLM Lab이라는 실제 프로젝트를 직접 만들면서 배우는 실습형 학습서입니다. "SLM"이나 "RAG" 같은 단어를 처음 들어도 괜찮습니다. 이론 설명을 먼저 쌓은 다음 실습으로 가는 대신, 우리가 실제로 무언가를 만드는 과정을 함께 따라가면서 필요한 개념을 그때그때 풀어냅니다.

각 챕터는 하나의 질문에 답합니다:

  • 1장 (지금 읽는 중) — 전체 지형도. 왜 이걸 만드는가, 무엇을 만드는가, 어떤 순서로 가는가.
  • 2장 — RAG 파이프라인을 해부. 문서가 어떻게 조각나고, 검색되고, 모델 앞에 놓이는지.
  • 3장 — 실제로 실행해보기. 로컬에서 Gemma 3:4b 모델이 답하는 장면을 직접 확인.
  • 4장 — 측정과 가설. 어떤 질문엔 잘 답하고 어떤 질문엔 틀리는지, 왜 그런지 분석.
개념 SLM(Small Language Model)이란 파라미터 수가 수십억(billion) 규모 이하인 언어 모델을 가리킵니다. GPT-4나 Claude Opus 같은 대형 LLM(Large Language Model)과 달리, 개인 노트북이나 온프레미스 서버에서 GPU 없이 또는 소형 GPU로 실행할 수 있습니다. 이 랩에서는 Google의 Gemma 3:4b를 주로 사용합니다(파라미터 약 40억 개).

누가 읽으면 좋은가

다음 중 하나라도 해당된다면 이 책이 잘 맞습니다:

  • GPT·Claude 같은 AI를 써봤지만 내부가 궁금한 개발자
  • RAG나 파인튜닝이라는 단어는 들었지만 직접 구현해본 적 없는 분
  • magicJar 프로젝트를 알고 있고, 그 위에 AI를 얹는 과정이 궁금한 분
  • 클라우드 API 비용 없이 로컬에서 AI를 돌리고 싶은 분

Java·Spring·JavaScript에 대한 기본적인 이해가 있으면 코드 예제를 더 쉽게 따라갈 수 있습니다. 하지만 AI 원리 자체는 수식 없이 설명하므로 ML 배경은 필요하지 않습니다.

2. 최종 목표 한 문장

이 랩의 목표를 한 문장으로 쓰면 다음과 같습니다:

"Opus·Fable 같은 큰 LLM이 magicJar에 대해 내놓는 좋은 답을 '자산'으로 삼아, 로컬 SLM(Gemma 3:4b)이 LLM 없이도 magicJar 채팅 질문에 Opus만큼 답하게 만든다."

이 문장에는 중요한 단어가 세 개 있습니다. 하나씩 뜯어봅시다.

'큰 LLM의 좋은 답을 자산으로'

Claude Opus나 Anthropic Fable 같은 대형 모델은 이미 magicJar 문서, 소스코드, 거래 개념을 잘 이해합니다. 이 모델들이 특정 질문에 내놓는 답은 고품질 정답 예시입니다. 우리는 그 답을 한 번 생성해서 기록해두고, 이후에는 클라우드 API를 더 이상 호출하지 않습니다. 비유하자면, 실력 있는 선배가 어려운 문제를 풀어줬고 그 풀이를 교재로 만드는 것입니다.

'로컬 SLM이 LLM 없이도'

최종 상태에서 서비스는 인터넷 연결 없이 온프레미스에서 작동합니다. 클라우드 API 비용, 지연 시간, 데이터 외부 전송 우려가 모두 사라집니다. Ollama로 로컬 실행되는 Gemma 3:4b가 사용자 질문에 직접 답합니다.

'Opus만큼 답하게'

물론 4b 모델이 모든 면에서 Opus를 이길 수는 없습니다. 그러나 magicJar 도메인 안에서, 미리 정의된 질문 유형에 한해서는 Opus 수준에 가까운 답을 낼 수 있다는 것이 이 랩의 가설입니다. "의학 질문에도 잘 답해야 한다"는 목표가 아니라, "magicJar FVG가 뭔지 설명해줘" 같은 좁고 깊은 질문에 잘 답하는 것이 목표입니다.

가설 왜 범위를 좁히는가: 언어 모델은 파라미터가 많을수록 다양한 도메인을 커버합니다. 4b짜리 모델에 "세상 모든 것을 알아라"라고 요구하는 것은 무리입니다. 하지만 magicJar 문서와 코드라는 특정 말뭉치 안에서만 답하도록 집중시키면, 작은 모델도 큰 모델을 이길 수 있다는 것이 우리의 핵심 베팅입니다. 스포츠에 빗대면: 마라토너(Opus)와 단거리 스프린터(Gemma 4b)를 100m 달리기에서 붙이는 전략입니다.

3. 세 가지 메커니즘 구분

AI 모델을 특정 도메인에 잘 답하게 만드는 방법은 크게 세 가지입니다: 프롬프팅(Prompting), RAG(Retrieval-Augmented Generation), 그리고 파인튜닝/증류(Fine-tuning / Distillation). 이 세 가지의 차이를 이해하는 것이 이 랩 전체의 지도를 읽는 열쇠입니다.

방법 가중치 변경? 무엇을 잘하나 주요 한계 비용·복잡도
프롬프팅 아니오 즉각적인 행동 조정, 역할 부여, 출력 형식 지정 모델이 원래 모르는 정보는 여전히 모름. 환각 위험. 매우 낮음
RAG 아니오 외부 문서 기반 답변, 최신 정보 반영, 출처 제공 검색이 실패하면 답 품질이 떨어짐. 긴 문서 처리 한계. 중간 (임베딩·검색 인프라 필요)
파인튜닝/증류 예 도메인 지식을 가중치에 내재화. 인퍼런스 시 문서 불필요. 훈련 데이터·GPU 필요. 업데이트 주기가 느림. 높음 (GPU, 데이터 파이프라인, 훈련 시간)
개념 가중치(weight)란 모델이 학습을 통해 얻은 수십억 개의 숫자입니다. 프롬프팅과 RAG는 이 숫자를 건드리지 않고 모델의 입력을 바꿉니다. 파인튜닝과 증류는 이 숫자 자체를 조정합니다. 가중치를 바꾸면 영구적으로 모델의 '기억'이 달라집니다.

이 랩에서 세 가지의 역할

이 랩의 최종 목표는 증류입니다. 가중치를 바꿔서 모델에 magicJar 지식을 베껴 넣는 것이죠. 그러나 증류는 훈련 데이터가 필요합니다. 좋은 (질문, 답변) 쌍이 수백~수천 개 있어야 합니다.

RAG가 두 가지 역할을 합니다:

  1. 즉각적인 답변 개선 (지금, Phase 1): 증류 없이도 지금 당장 "되네?"를 확인할 수 있게 합니다. magicJar 문서를 벡터 DB에 넣고 검색해서, 모델 앞에 관련 컨텍스트를 주면 Gemma 3:4b도 꽤 좋은 답을 냅니다.
  2. 증류 훈련 데이터 공장 (나중, Phase 3 준비): RAG로 사용자 질문을 받고 Opus가 답하게 하면, 그 (질문→Opus답) 쌍이 자동으로 쌓입니다. 이것이 나중에 Gemma를 파인튜닝할 훈련 데이터가 됩니다.
비유 요리 학교 비유: 프롬프팅은 요리사에게 레시피 카드를 주는 것. RAG는 요리하는 도중 조리대에 재료와 레시피 책을 올려두는 것. 파인튜닝/증류는 요리사가 수백 번 연습해서 레시피 없이도 손이 기억하게 만드는 것. 우리는 결국 세 번째를 원하지만, 일단 두 번째 방법으로 맛을 확인하고 연습 데이터를 모읍니다.

4. 지식 증류(Knowledge Distillation)란

지식 증류는 2015년 Geoffrey Hinton 팀이 제안한 개념으로, 큰 선생(teacher) 모델의 행동을 작은 학생(student) 모델에 베껴 넣는 훈련 기법입니다.

질문 데이터셋
magicJar 관련 질문 수백 개
↓
Teacher Model (Claude Opus)
각 질문에 고품질 답 생성
↓
훈련 데이터셋
(질문, Opus 답변) 쌍 수백~수천 개
↓
Student Model Fine-tuning
Gemma 3:4b를 그 쌍으로 훈련
↓
증류된 Gemma 3:4b
Opus 없이도 magicJar 질문에 잘 답함

일반 파인튜닝과 무엇이 다른가

일반 파인튜닝은 사람이 직접 만든 (질문, 정답) 쌍으로 훈련합니다. 증류는 다른 AI 모델이 만든 답을 정답으로 씁니다. 이렇게 하면 사람이 일일이 정답을 작성하는 수고 없이, 대형 모델의 추론 능력을 작은 모델에 전달할 수 있습니다.

개념 소프트 레이블(soft label): 증류의 원래 기법은 선생 모델의 확률 분포 자체를 학습시킵니다. 예를 들어 "FVG"라는 단어 다음에 "는", "란", "이란" 이 세 단어가 각각 40%, 35%, 25% 확률로 올 수 있다는 정보를 학생이 통째로 배우는 것입니다. 이 책의 PoC 단계에서는 완전한 소프트 레이블보다 간단한 SFT(Supervised Fine-Tuning) 방식을 씁니다. 선생 답변 텍스트를 정답으로 삼는 것이죠.

magicJar 맥락에서의 증류

현재 magicJar의 StrategyResearchAiTextClient 인터페이스 뒤에 Opus나 Fable이 붙어 있다고 상상해봅시다. 사용자가 "FVG 기반 전략을 어떻게 설정하나요?"라고 물으면 Opus가 답합니다. 우리는 그 질문과 답변을 파일로 저장합니다. 수백 개가 모이면 Gemma 3:4b를 그것으로 훈련합니다. 이후 클라이언트 뒤에 Gemma가 붙어도 사용자는 비슷한 품질의 답을 받습니다 — 로컬에서, 무료로.

비유 도제 제도 비유: 장인(Opus)이 수년간 쌓은 비법을 10분짜리 답변으로 설명해주면, 도제(Gemma 3:4b)가 그 설명을 수백 번 필사하며 손에 익힙니다. 도제는 나중에 장인 없이도 그 기술을 써먹을 수 있게 됩니다. 단, 새로운 기술이 생기면 다시 필사 과정을 거쳐야 합니다 — 그게 재훈련 주기입니다.

5. 왜 RAG부터 시작하는가

지식 증류가 최종 목표라면, 왜 지금 당장 증류를 하지 않고 RAG부터 할까요? 두 가지 실용적인 이유가 있습니다.

이유 1: 훈련 0초 — 빠른 피드백

RAG는 모델 가중치를 전혀 바꾸지 않습니다. 문서를 임베딩해서 벡터 DB에 넣고, 질문이 오면 관련 조각을 검색해서 프롬프트에 붙이면 끝입니다. 이 과정은 GPU 없이, 수 시간이 아니라 수 분 만에 셋업할 수 있습니다.

"우리 도메인에서 작은 모델이 쓸만한 답을 내는가?"라는 가설을 확인하는 데 RAG가 가장 빠른 실험 도구입니다. 결과가 너무 나쁘다면 증류에 투자하기 전에 방향을 바꿀 수 있습니다.

이유 2: 데이터 공장 — 증류 준비

RAG 파이프라인을 통해 실제 사용자 질문이 들어오고, Opus가 그에 답합니다. 그 (질문, 답변) 로그를 자동으로 누적시키면, 별도의 데이터 수집 작업 없이 증류 훈련 데이터셋이 만들어집니다. Phase 1(RAG)은 Phase 3(증류) 데이터 공장이기도 합니다.

사용자 질문 입력
"FVG 기반 전략 설정 방법은?"
↓
RAG 검색
벡터 DB에서 관련 문서 조각 추출
↓
Opus 호출
컨텍스트 + 질문 → 고품질 답변 생성
↓
답변 반환 + 로깅
사용자에게 답 표시, (질문, 답) 파일 저장
↓
증류 데이터 축적
나중에 Gemma 파인튜닝에 사용
가설 RAG만으로도 충분하지 않을까? RAG는 검색이 성공할 때만 좋은 답을 냅니다. 문서에 없는 질문, 오래된 문서, 애매한 쿼리에서는 성능이 떨어집니다. 반면 증류된 모델은 검색 없이도 기억에서 꺼냅니다. 우리는 최종적으로 RAG+증류 조합이 RAG 단독보다 강건하다고 가설을 세웁니다. Phase 4에서 실험으로 검증할 예정입니다.

6. 현실 직시: 4b 모델로 무엇이 가능하고 불가능한가

Gemma 3:4b는 놀랍도록 유능하지만, 한계도 명확합니다. 랩을 시작하기 전에 기대치를 솔직하게 설정하는 것이 중요합니다.

가능한 것
  • 좁은 도메인에서 문서 기반 Q&A
  • 짧은 텍스트 요약 및 설명
  • 단순한 코드 스니펫 설명 (읽기·이해)
  • 도메인 특화 후 FAQ 수준 답변
  • 정해진 형식(JSON, 리스트)으로 출력
주의
  • 광범위한 일반 지식 질문 → 환각 위험
  • 복잡한 다단계 추론 → 오류 가능성 높음
  • 코드 자동 수정·생성 → 후순위
  • 에이전틱 도구 실행 → 아직 실험적
  • 긴 컨텍스트(32k+) 처리 → 성능 저하

이 랩의 전략은 "좁히면 된다"는 것입니다. "magicJar의 FVG 오더블록 전략을 언제 활성화하나요?" 같은 질문은 관련 문서를 컨텍스트로 주면 4b 모델도 상당히 잘 답합니다. 반면 "오늘 어떤 종목을 사야 할까요?"처럼 현재 시장 데이터와 판단이 필요한 질문은 아무리 좋은 모델도 AI만으로 답해서는 안 됩니다 — 이건 기술의 한계이기도 하지만, 이 랩의 안전 원칙이기도 합니다(8절 참조).

채팅 Q&A부터 시작하는 이유

코드 수정, 전략 자동 생성, 에이전틱 실행 같은 기능은 훨씬 강한 추론 능력이 필요합니다. 채팅 Q&A는 그 중에서 가장 검증하기 쉽고, 실패해도 피해가 없습니다. "답이 틀렸다"는 피드백을 빠르게 받을 수 있고, 그 피드백이 곧 훈련 데이터 개선으로 이어집니다. 복잡한 것은 나중에, 쉬운 것은 지금 — 이것이 Phase 설계의 원칙입니다.

더 알고 싶다면: 파라미터 수와 능력의 관계

언어 모델의 파라미터 수는 대략적인 "기억 용량"과 "추론 깊이"에 비례합니다. GPT-4는 수백~1,000b 수준, Claude Opus는 수백b 수준으로 추정됩니다. Gemma 3:4b는 이의 약 1/100 수준입니다.

그러나 파라미터 수가 전부는 아닙니다. 훈련 데이터의 품질, 미세조정 방식, 그리고 무엇보다 태스크 범위를 얼마나 좁히느냐가 큰 차이를 만듭니다. Phi-2(2.7b)가 특정 코딩 태스크에서 GPT-3.5를 이긴 사례, TinyLlama가 특화 도메인에서 놀라운 성능을 보인 사례가 여럿 있습니다. 

# 파라미터 수 개요 (대략적인 공개 추정치)
Gemma 3:4b     →  ~4 billion params  (노트북 실행 가능)
Llama 3.1 8b   →  ~8 billion params  (소형 GPU)
Llama 3.1 70b  →  ~70 billion params (고사양 GPU 필요)
Claude Opus    →  수백 billion 이상  (클라우드 전용)

7. 단계 로드맵

이 랩은 네 단계로 나뉩니다. 각 단계는 이전 단계의 결과물 위에 쌓입니다.

현재 위치
기반 인프라 셋업 완료
↓
Phase 1 — RAG Q&A (완료)
문서 임베딩 → 벡터 검색 → Gemma/Opus 답변

종착점
로컬 전용 magicJar 도메인 어시스턴트 (MOCK)

이 책은 Phase 1을 중심으로 씁니다. Phase 1이 완성된 상태에서 출발하며, 각 챕터는 파이프라인의 한 부분씩을 자세히 살핍니다. Phase 2~4는 로드맵으로만 소개하고, 추후 챕터가 추가될 예정입니다.

개념 PoC(Proof of Concept): 이 랩은 상용 서비스가 아니라 PoC입니다. "원칙적으로 가능한지" 빠르게 확인하는 것이 목적입니다. 코드가 다소 거칠거나 하드코딩이 있어도 괜찮습니다. 단, 안전 경계(8절)만은 타협 없이 지킵니다.

8. 안전 경계 — 이것은 협상의 여지가 없다

이 랩은 실험 환경입니다. 그러나 하나의 규칙은 실험이 아닙니다:

이 랩의 AI는 설명하고 초안을 잡는다. 매매, 주문, 전략 활성화, 실계좌 변경은 절대 하지 않는다.

구체적으로 금지된 것들

  • 실제 KIS(한국투자증권) API로 주문 전송
  • 라이브 Kafka 주문 토픽에 메시지 발행
  • 전략 활성화 또는 비활성화 상태 변경
  • 실계좌 잔고·포지션 변경
  • SLM 출력을 검증 없이 자동으로 실행 경로에 연결

기술적으로 어떻게 강제하는가

랩 실행 환경은 항상 다음 두 환경 변수를 유지합니다: 

MAGICJAR_MODE=MOCK
MAGICJAR_ALLOW_REAL=false

이 설정에서는 주문 관련 코드가 실제 API를 호출하지 않고 Mock 응답을 반환합니다. Docker Compose 파일도 원본 magicJar 스택과 완전히 분리된 포트와 볼륨을 사용합니다. 실수로도 실계좌에 영향을 줄 수 없도록 설계되어 있습니다.

왜 이게 1급 원칙인가

AI 모델은 확률적으로 동작합니다. 같은 질문에도 답이 달라질 수 있고, 드물게 완전히 틀린 답을 자신있게 내놓기도 합니다(이를 환각(hallucination)이라 합니다). 이런 출력이 매매 주문으로 연결된다면, 작은 버그 하나가 실제 재무 손실로 이어집니다.

AI 어시스턴트의 적절한 역할은 판단의 보조이지 판단의 대리가 아닙니다. "이 패턴은 FVG 조건을 충족하는 것 같습니다"라고 설명하는 것과, "자동으로 매수 주문을 실행합니다"는 완전히 다른 행위입니다. 이 랩은 전자를 탐색하고, 후자는 영구히 금지합니다.

주의 랩 코드를 수정할 때 주문·리스크·KIS 자격증명·Kafka 주문 토픽·소비자 실행 경로를 건드리는 변경이 필요하다고 느껴지면, 먼저 멈추고 안전 영향을 명시적으로 서술하십시오. 이 랩에서 그 경계를 넘는 코드는 작성하지 않습니다.
더 알고 싶다면: 왜 LLM 자율 에이전트는 금융에서 더 위험한가

일반적인 소프트웨어 버그는 "예외 발생 → 서비스 중단"으로 끝나는 경우가 많습니다. 하지만 AI가 실행 권한을 가진 경우, 오류가 조용히 잘못된 행동을 완료할 수 있습니다. 주문 시스템에서 이것은 원치 않는 포지션, 의도치 않은 매도, 리스크 한도 초과를 의미합니다.

2010년 Flash Crash, 2012년 Knight Capital 알고리즘 사고 등 자동화 거래 시스템의 오작동이 단 수십 분~수 시간 만에 수억 달러 손실로 이어진 사례들이 있습니다. AI는 기존 알고리즘보다 오류 모드를 예측하기 훨씬 어렵다는 점에서 더 주의가 필요합니다. 따라서 이 랩은 AI를 읽기·설명 전용으로만 씁니다.

정리: 이 장에서 기억할 것

다음 표는 이 장의 핵심을 요약합니다:

키워드 한 줄 요약
SLM 로컬에서 실행 가능한 소형 언어 모델. 이 랩은 Gemma 3:4b 사용.

최종 목표 Gemma 3:4b가 magicJar 도메인에서 Opus 수준으로 답하게 만들기.

절대 금지 AI 출력으로 주문·전략활성화·실계좌 변경. MOCK 전용.
