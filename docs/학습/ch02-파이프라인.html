Chapter 2

RAG 파이프라인 해부: 입력·출력·파라미터 + 실측 데이터

질문 한 개가 답이 되기까지 — 6단계 각각의 입력/출력/파라미터를, 우리가 실제로 돌린 진짜 데이터로 따라간다.

1. 두 시점: 인덱싱(미리) vs 질의(매번)

RAG에는 시간적으로 완전히 다른 두 단계가 있다. 인덱싱(Indexing)은 미리 한 번 실행되고, 질의(Query)는 사용자가 질문할 때마다 실행된다. 이 둘을 구분하지 않으면 "왜 빠르지?" vs "왜 느리지?"를 잘못 이해하게 된다.

핵심 개념 인덱싱은 "도서관 색인 카드 만들기"다. 책이 바뀌지 않는 한 매번 만들 필요가 없다. 질의는 "색인 카드를 뒤져 책 내용을 찾아 요약"하는 것으로, 매번 실행된다. 이 설계 덕분에 수천 개 파일을 가진 레포에서도 질의 속도를 일정하게 유지할 수 있다.

단계 0 · 코퍼스 큐레이션: 무엇을 인덱싱 대상으로 고를까?

RAG의 품질은 "무엇을 집어넣느냐"에서 절반이 결정된다. 쓸모없는 파일을 많이 넣으면 잡음이 늘어나고, 중요한 파일을 빠뜨리면 답을 못 찾는다. 그리고 비밀 파일을 잘못 넣으면 보안 사고가 된다.

안전 주의 .env, application-prod.yml, KIS API 키, JWT 시크릿이 포함된 파일은 절대 인덱싱하면 안 된다. 벡터DB에 저장된 텍스트는 LLM이 답변 속에 그대로 노출할 수 있다. 우리 랩은 MAGICJAR_MODE=MOCK 환경이므로 실 시크릿이 없지만, 인덱서가 .env*, *.secret, build/, node_modules/를 제외 목록에 넣는 것이 기본 원칙이다.

입력레포 루트 디렉터리 전체 (magicjar-slm-poc/)

실측값 71개 파일 → 1,095 청크. 이 중 Kotlin 소스(.kt)가 대다수를 차지하며, architecture 폴더의 Markdown 문서들도 포함되어 있다. 선정된 71개 파일이 곧 우리 RAG 시스템이 "아는 세계"의 전부다.
가설 71개 파일은 전체 레포에서 코드·문서에 해당하는 핵심 파일만 고른 결과다. 빌드 산출물이나 테스트 픽스처를 포함했다면 청크 수가 수천 개로 늘어나고, 검색 잡음이 증가했을 것이다. 품질과 양의 트레이드오프가 단계 0에서 이미 결정된다.

단계 1 · 청킹: 왜 파일을 조각내는가?

임베딩 모델에는 입력 길이 한계(BGE-M3는 512 토큰)가 있다. 또 검색할 때 "파일 전체"보다 "관련 함수 하나"가 훨씬 정밀하게 매칭된다. 그래서 파일을 의미 단위로 잘라 각 조각을 독립적으로 임베딩한다.

코드와 문서는 쪼개는 기준이 다르다:

  • 코드(.kt, .ts 등): 최상위 선언 경계(class, object, fun, data class)를 기준으로 분할. 한 클래스 안의 메서드가 하나의 청크 단위가 된다.
  • 문서(.md): 헤딩(#, ##, ###)을 기준으로 섹션 단위로 분할.

입력 / 출력 / 파라미터

구분내용
입력큐레이션된 파일 71개 (텍스트 내용 전체)
출력청크 1,095개. 각 청크: {file_path, start_line, end_line, kind, text}
파라미터: 코드 분할 전략최상위 선언 경계(top-level declaration boundary)
파라미터: 문서 분할 전략Markdown 헤딩(h1~h3)
파라미터: kindcode 또는 markdown (검색 결과에 표시)
비유 책을 통째로 스캔하면 "어느 페이지에 뭐가 있는지" 찾기 어렵다. 챕터별로 인덱스 카드를 만들어야 "2장 3절"을 빠르게 찾을 수 있다. 청킹은 그 인덱스 카드 단위를 결정하는 과정이다. 너무 잘게 쪼개면(한 줄씩) 맥락이 사라지고, 너무 크게 묶으면(파일 전체) 임베딩이 뭉개진다.
가설 1번 검색 결과인 StrategyResearchController.kt:26-296는 한 청크가 270줄이다. 이 크기면 512 토큰 임베딩 한계에 근접하거나 초과할 수 있다. 실제로 임베딩 단계에서 잘릴 가능성이 있으며, 이것이 점수가 0.63으로 중간 수준에 머무는 원인 중 하나일 수 있다.

단계 2 · 임베딩(BGE-M3): 글을 1024차원 의미 좌표로

임베딩은 텍스트를 숫자 벡터로 바꾸는 과정이다. 비슷한 의미의 텍스트는 이 공간에서 가까이 놓이고, 무관한 텍스트는 멀리 놓인다. 우리는 BAAI/bge-m3 모델을 사용하는데, 이 모델은 한국어·영어·코드를 모두 이해하는 다국어 모델이다.

비유 도시들을 지도 위에 점으로 찍으면 서울과 인천은 가깝고, 서울과 부산은 멀다. 임베딩은 텍스트 조각들을 1024차원 "의미 지도" 위에 찍는 과정이다. "RSI 과매도 매수"라는 질문과 "rsi < 30일 때 진입" 코드 청크는 이 지도에서 가까운 위치에 놓인다.

입력 / 출력 / 파라미터

구분내용
입력청크 텍스트 1개 (문자열)
출력1024차원 부동소수점 벡터 (float32 × 1024)
파라미터: modelBAAI/bge-m3
파라미터: max_length512 토큰 (초과분은 잘림)
파라미터: normalizeTrue (코사인 유사도 계산을 위해 단위 벡터로 정규화)
처리 방향인덱싱 시: 청크 1,095개 전체 임베딩 후 저장 / 질의 시: 질문 텍스트만 임베딩
주의: 512 토큰 잘림 BGE-M3의 입력 한계는 512 토큰이다. 한국어 기준으로 1토큰 ≈ 1~2 글자, Kotlin 코드 기준으로 1토큰 ≈ 3~5 글자 수준이다. StrategyResearchController.kt:26-296 같은 270줄짜리 청크는 이 한계를 훌쩍 넘어서 뒷부분이 잘린 채로 임베딩된다. 즉, 그 청크의 하단 메서드들은 사실상 벡터에 반영되지 않는다. 청크를 더 작게 쪼개거나(overlap chunking), max_length를 늘릴 수 있는 모델로 교체하는 것이 개선 방향이다.

단계 3 · Qdrant 적재/검색: 벡터DB에서 가장 가까운 이웃 찾기

Qdrant는 벡터를 저장하고 빠르게 검색하는 데이터베이스다. 인덱싱 시에 1,095개 청크의 벡터를 모두 저장해 두고, 질의 시에 질문 벡터와 가장 가까운(코사인 유사도가 높은) top-k개를 반환한다.

입력 / 출력 / 파라미터

구분내용
입력 (적재)청크 벡터 1,095개 + 메타데이터(file_path, start_line, end_line, kind, text)
입력 (검색)질문 벡터 1개 (1024차원)
출력 (검색)top-k 청크 목록, 각 청크에 코사인 유사도 점수 포함
파라미터: top_k5 (상위 5개 청크 반환)
파라미터: similarity코사인 유사도 (Cosine Similarity, 0~1, 높을수록 유사)
파라미터: collectionmagicjar-slm-poc 레포 전용 컬렉션

단계 4 · 프롬프트 조립: 안전 가이드 + 증거 + 질문

검색으로 찾은 청크들을 모델에게 전달하기 위해 하나의 텍스트로 조립한다. 이 조립 방식이 답변 품질을 크게 좌우한다. 특히 시스템 프롬프트는 모델이 무엇을 해야 하는지, 무엇을 하면 안 되는지를 명시하는 안전 경계다.

구분내용
입력① 시스템 프롬프트 (고정 텍스트) + ② top-5 청크 텍스트 + 메타데이터 + ③ 사용자 질문
출력완성된 프롬프트 문자열 (demo_system: 20,035자)
형식: 컨텍스트 출처 표기각 청크를 [n] 출처: {file_path}:{start_line}-{end_line} (kind={kind}) 형식으로 번호 붙여 나열

2.  **내 전략 추가:** 사용자가 저장한 전략(dsl_entry·손절/익절)을 리서치 후보로 승격할 수 있습니다.

4.  **AI 종목 발굴:** `ai-discovery` 엔드포인트를 통해 Claude CLI를 활용하여 사용자 자연어 쿼리에
