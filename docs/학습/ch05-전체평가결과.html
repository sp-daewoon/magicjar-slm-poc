전체 평가 결과 & 해석: 30문항을 돌려보니

처음으로 30문항을 전부 돌린 진짜 결과 — 숫자보다 더 큰 교훈은 "측정 자체가 어렵다"였다.

1. 무엇을 돌렸나

4장에서 설계한 평가 파이프라인을 실제로 30문항 전부에 돌렸습니다. 각 문항마다 세 번의 LLM 호출이 연결됩니다:

① Gemma + RAG → 답변 생성 ② Opus → 같은 질문에 정답 답변 생성 ③ Opus → 두 답변 비교 심판 (점수 + 승자)

문항 30개 × 3회 = 90회 LLM 호출이 이론상 필요합니다. 실제로는 Gemma 호출 30회 + Opus 호출 60회 (답변 30 + 심판 30) 구조입니다. 강건화된 러너(eval_runner.py)는 재시도 로직(최대 2회, 각 300초 타임아웃)을 갖추고 있었고 30문항 전부를 완주했습니다.

아래는 평가가 끝난 뒤 생성된 results.md의 Summary 섹션을 그대로 옮긴 것입니다:

3. 가장 큰 발견: 20문항이 실패했다

주의

20문항(67%)은 심판 점수가 없습니다. 이것은 모델 품질 문제가 아니라 측정 인프라 문제입니다. Gemma가 나쁜 답을 해서가 아니라, Opus 심판 호출이 실패해서 점수 자체를 기록하지 못했습니다.

무슨 일이 벌어졌는지 구체적으로 보겠습니다.

각 문항에 대해 Opus를 두 번 호출합니다 — 답변 1회 + 심판 1회. 30문항이면 60회의 순차 Opus 호출이 발생합니다. 우리가 쓴 Opus "다리"는 로컬 claude CLI를 subprocess로 호출하는 방식입니다. 재시도 설정은 최대 2번, 각 300초입니다.

q01 ~ q10은 성공했습니다. q11부터 Opus 호출이 연속으로 실패하기 시작했고, 재시도로도 회복하지 못했습니다. 에러 행에는 winner=error만 남았습니다.

이 20건의 실패는 이 장에서 가장 중요한 발견입니다. 평가 점수가 낮게 나왔다거나 Gemma가 모든 문항에서 졌다는 것보다 훨씬 더 근본적인 문제입니다. "측정 인프라도 실험 대상"이라는 교훈입니다 — 측정 도구가 신뢰할 수 없으면, 측정 결과도 신뢰할 수 없습니다.

개념

측정 인프라도 실험 대상이다: 실험에서 모델(Gemma)만 시험대에 오른 것이 아닙니다. 평가 파이프라인 — Opus 다리, CLI subprocess, 재시도 로직, 직렬 호출 구조 — 도 함께 시험대에 올랐습니다. 그리고 이번에는 평가 파이프라인이 먼저 실패했습니다. 이것을 숨기지 않고 기록하는 것이 Phase 1의 진짜 가치입니다.

4. 왜 실패했나 — 가설 세 가지

가설 A

레이트 리밋 / 스로틀링

Claude CLI는 내부적으로 Anthropic API를 호출합니다. 짧은 시간 안에 60회가 순차 발화되면 사용량 제한에 걸릴 수 있습니다. q01~q10이 성공하고 q11부터 연속 실패한 패턴은 "일정 호출 수 이후 지속 제한"과 일치합니다.

가설 B

중첩 Claude 프로세스 경합

평가 러너 자체가 Claude Code 환경 안에서 실행될 수 있습니다. 바깥 Claude 세션과 안쪽 subprocess Claude CLI가 같은 인증 토큰·소켓을 두고 경합하면 타임아웃이 길어집니다. 300초 타임아웃을 써도 못 살린 것은 일시적 멈춤이 아니라 지속 차단 때문일 가능성이 있습니다.

가설 C

직렬 구조의 누적 지연

문항당 평균 35.3초입니다. 10문항이면 약 353초입니다. 재시도 포함 시 이후 문항들은 누적 대기 시간이 폭발적으로 늘어납니다. 하나가 실패하고 600초(2×300s) 재시도 후 포기하면, 그 뒤 문항들은 더욱 불리한 시점에 호출됩니다.

세 가설 모두 "직렬 60회 subprocess CLI 호출"이라는 설계에서 비롯됩니다. 어느 한 가설만 맞는 게 아니라 셋이 복합적으로 작용했을 가능성이 높습니다.

5. 다음엔 이렇게 — 측정 인프라 고치기

모델 성능을 올리기 전에 먼저 평가 파이프라인을 신뢰할 수 있게 만들어야 합니다. 구체적인 개선 방향입니다:

문제 개선 방향 기대 효과
Opus를 문항당 2회 호출 (답변 + 심판) 답변+심판을 1회 프롬프트로 합치기 60회 → 30회로 절반
Opus 답변이 문항마다 반복 생성 Opus 답변 캐싱 (질문 해시 → 답변 파일) 재실행 시 Opus 호출 0회
연속 호출로 레이트 리밋 유발 호출 간 지수 백오프 + 지연 추가 제한 회피 가능성 상승
subprocess CLI 방식 — 불안정 CLI 대신 Anthropic Python SDK (API 직접) 사용 프로세스 경합 제거, 에러 투명화
직렬 처리 — 느리고 누적 실패 소규모 배치 병렬 처리 (예: 5문항씩) 총 소요 시간 단축

이 중 "Opus 답변 캐싱"이 가장 즉각적인 효과를 냅니다. 캐시가 있으면 재실행 시 Gemma 호출 30회 + Opus 심판 호출 30회만 하면 됩니다. 답변 캐시를 git에 커밋해두면 팀원이 동일한 기준으로 결과를 재현할 수도 있습니다.

## StrategyResearchAiTextClient의 역할과 반환값

### 한 줄 요약
이 인터페이스는 "프롬프트(문자열)를 받아 AI 텍스트 응답을 돌려주는 단일 경계"입니다.

fun interface StrategyResearchAiTextClient {
    fun complete(prompt: String): StrategyResearchAiTextResult
}

반환값 StrategyResearchAiTextResult:
  val provider: String  // "claude-cli", "claude-cli-bridge"
  val text: String      // AI가 생성한 원본 텍스트 (raw, 미가공)

### 역할의 경계 — 무엇을 "하지 않는가"가 핵심
프롬프트 빌드 / JSON 파싱 / instrument 매칭 / 검증은 전부 인터페이스 바깥
(서비스)에 두고, 이 경계는 "텍스트를 받아오는 일"만 책임집니다.
...(이하 구현체·실패 처리·설계 의도 상세 설명 생략)

왜 이 점수인가 — 해석

Gemma 답(4점)은 핵심 사실을 정확히 맞혔습니다 — provider와 text 필드, 역할 설명 모두 RAG 컨텍스트에서 잘 추출됐습니다. 다만 "이 인터페이스가 하지 않는 것" (파싱·검증·매칭이 서비스 바깥에 있다는 설계 의도)은 설명하지 못했습니다. Opus는 실제 코드 라인 번호와 함께 구현체·실패 처리·provider 교체 전략까지 답했습니다. 4점은 "사실은 맞지만 깊이에서 차이"를 반영합니다. RAG가 제대로 된 컨텍스트를 찾아줄 때 Gemma가 어디까지 갈 수 있는지를 보여주는 최선의 사례입니다.

2. 이름/코드 검색 (:861-874): [이름, 정규화 이름, 코드, 정규화 코드] 순으로 검색

왜 이 점수인가 — 해석

Gemma 답(2점)은 틀린 위치를 가리켰습니다. "Screener 단계"라고 했는데, 실제 종목 매칭은 Screener(자동매매 흐름)가 아니라 AI 호출 직후 JSON 파싱 → DTO 변환 시점에 일어납니다. RAG 컨텍스트에 "Screener" 관련 문서가 들어있어서 그쪽으로 답변이 끌려간 것으로 보입니다 — RAG가 잘못된 컨텍스트를 주면 오히려 없는 것보다 나쁜 답이 나올 수 있다는 것을 보여주는 사례입니다. Opus는 코드를 직접 검색해 정확한 라인 번호와 2단계 매칭 전략(코드 우선 → 이름 검색)을 답했습니다. 2점의 의미: 방향이 크게 어긋났고 사용자가 이 답을 믿으면 잘못된 곳을 탐색하게 됩니다.
