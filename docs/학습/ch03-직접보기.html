Chapter 3

직접 보기: Phoenix · Streamlit · Qdrant 관측 가이드

RAG는 눈으로 봐야 이해된다 — 무엇이 검색됐고, 어떤 프롬프트가 갔고, 어디에 저장됐는지 실제로 보는 법.

먼저: 세 개의 창구

이 챕터에서 실제로 열어 볼 화면은 딱 세 개입니다. 겁먹지 마세요 — 브라우저 탭 세 개면 충분합니다.

도구 URL 무엇을 보나 한 마디로
Streamlit localhost:18501 질문 입력 → 검색된 청크 → 실제 프롬프트 → 답변을 한 화면에서 체험 체험·내부 펼침
Arize Phoenix localhost:16006 질의마다 retrieve→LLM 스팬, 청크·점수·지연을 타임라인으로 해부 현업식 트레이스 해부
Qdrant localhost:16333/dashboard 벡터 DB에 저장된 청크 수, 차원, 거리 함수, 개별 포인트 payload 확인 저장된 벡터 확인
비유

Streamlit은 운전석입니다. 직접 핸들을 잡고 RAG가 어떻게 반응하는지 느낍니다.
Phoenix는 블랙박스 리더입니다. 운전 후 기록을 열어 "그 순간에 정확히 무슨 일이 있었냐"를 밀리초 단위로 해부합니다.
Qdrant는 창고 대장입니다. 청크들이 실제로 어떻게 정렬돼 저장돼 있는지 직접 눈으로 확인합니다.

0단계 · 인프라 켜기

세 화면을 열기 전에 도커 컨테이너와 ollama 모델이 살아 있어야 합니다. 터미널 두 개를 열고 순서대로 실행하세요.

cd slm-lab
uv run streamlit run rag/app.py --server.port 18501

터미널에 You can now view your Streamlit app in your browser.가 보이면 준비 완료입니다.

③ 각 URL이 떴는지 확인

  1. 브라우저에서 http://localhost:18501 접속 → Streamlit 채팅 화면이 보이면 OK.
  2. 브라우저에서 http://localhost:16006 접속 → Phoenix 대시보드가 보이면 OK.
  3. 브라우저에서 http://localhost:16333/dashboard 접속 → Qdrant 대시보드가 보이면 OK.
  4. 안 보인다면 docker compose -f docker/docker-compose.slm-rag.yml ps로 상태를 확인하세요.

User: FVG 전략에서 포지션 진입 조건은 어떻게 설정하나요?
🤖 답변: FVG 전략의 진입 조건은 enter_long() 메서드에 구현돼 있습니다. 핵심은 가격이 FVG 상단(upper)을 종가 기준으로 재돌파할 때 롱 진입 신호를 생성하는 것입니다. 파라미터로 min_gap_pct: 0.003(최소 갭 크기 0.3%)와 entry_confirm: close_above_upper(종가 확인)가 사용됩니다.
질문을 입력하세요…

여기서 무엇을 관찰해야 하나

  1. Top-K 슬라이더를 바꿔보세요. K=1일 때와 K=5일 때 답변 품질이 어떻게 달라지는지 비교합니다.
  2. ①검색된 청크를 펼치세요. 점수(0~1)가 높을수록 질문과 더 유사한 벡터입니다. 가장 높은 청크가 정말 관련 있는 내용인지 확인하세요.
  3. ②최종 프롬프트를 펼치세요. 모델이 진짜로 받은 컨텍스트가 이것입니다. "왜 이런 답이 나왔나"는 항상 여기에 원인이 있습니다.
  4. 모호한 질문을 넣어보세요. 예: "전략 써줘". 청크 점수가 낮고 답변이 불명확해집니다 — 이것이 RAG의 한계입니다.
  5. 같은 질문을 한 뒤 다음 섹션의 Phoenix로 넘어가 트레이스를 해부하세요.
가설 만들기

청크 점수가 0.5 이하인 결과만 나왔다면, 그 청크가 답변에 포함됐나요? "모델은 낮은 점수 청크도 충실히 반영한다"는 가설을 세우고 실험해 보세요. Phoenix에서 프롬프트 토큰 수도 함께 확인하면 더 정확합니다.

클릭 순서 — Phoenix에서 한 질의를 해부하는 법

  1. http://localhost:16006을 열면 트레이스 목록이 보입니다. 가장 위(최신)가 방금 Streamlit에서 넣은 질문입니다.
  2. 트레이스 행을 클릭하면 오른쪽(또는 아래)에 스팬 타임라인이 펼쳐집니다. retrieve와 llm 두 스팬이 핵심입니다.
  3. retrieve 스팬을 클릭하세요 → 검색된 문서 경로와 코사인 유사도 점수가 나옵니다. Streamlit의 ①청크 펼침과 일치하는지 확인하세요.
  4. llm 스팬을 클릭하세요 → 실제로 모델에 들어간 프롬프트 전체, 입력/출력 토큰 수, 지연 시간이 보입니다.
  5. latency가 예상보다 크면 retrieve인지 llm인지 타임라인으로 원인을 좁힙니다. retrieve가 느리면 Qdrant 인덱스, llm이 느리면 ollama 모델을 점검합니다.
개념

스팬(Span)은 분산 추적에서 "의미 있는 작업 단위" 하나입니다. RAG에서는 보통 retrieve, llm, 그리고 이 둘을 감싸는 root 스팬으로 구성됩니다. Phoenix는 OpenTelemetry 프로토콜로 이 스팬들을 수집해 시각화합니다.

Qdrant에서 무엇을 확인하나

  1. http://localhost:16333/dashboard를 열고 magicjar_slm 컬렉션을 클릭하세요.
  2. 상단 통계에서 1,095 포인트, 차원 1024, Cosine 거리, 상태 green을 확인합니다. 이것이 벡터 인덱스의 현재 상태입니다.
  3. 아무 포인트나 클릭하면 payload(file_path, lines, kind)와 실제 벡터값(1024개 float)이 보입니다.
  4. Phoenix의 retrieve 스팬에서 나온 경로(strategies/fvg_strategy.py:42)를 Qdrant에서 검색해 payload가 일치하는지 대조해 보세요.
  5. "청크가 왜 검색됐나"를 의심할 때, Qdrant에서 직접 벡터 유사도 검색(Search 탭)을 해볼 수 있습니다.
개념

Qdrant에서 포인트 하나 = 청크 하나입니다. payload에는 원본 파일 경로와 줄 번호가 저장되고, 벡터에는 nomic-embed-text가 생성한 1024차원 임베딩이 저장됩니다. 검색할 때 Qdrant는 질문의 임베딩과 이 벡터들 사이의 코사인 유사도를 계산해 가장 가까운 top-K를 반환합니다.

세 화면을 함께 쓰는 법

각 화면을 따로 보는 것도 좋지만, 진짜 실력은 세 화면을 동시에 열고 하나의 질문을 추적할 때 생깁니다.

가설 예시 A

"답변이 엉뚱하다" → Streamlit ①청크를 보니 점수가 모두 0.4 이하. → Phoenix retrieve 스팬에서 최고 점수 확인. → Qdrant에서 해당 파일을 검색하니 청크가 너무 길게 잘렸음(payload lines 범위 400줄). → 청크 크기 조정이 필요하다는 가설.

가설 예시 B

"응답이 너무 느리다" → Streamlit은 3초 이상. → Phoenix 타임라인에서 llm 스팬이 2.8s. → retrieve는 0.2s로 정상. → 결론: ollama 모델 양자화 수준을 낮추거나 다른 모델로 교체해야 한다는 가설.
