magicJar 백그라운드 프로세스 인벤토리

조사 기준: @Scheduled, @KafkaListener, ApplicationRunner, @PostConstruct, @EventListener, 내부 Executor/Scheduler 사용처를 코드에서 직접 추적. 런타임 설정값에 따라 일부는 skip 또는 no-op 될 수 있다.

핵심 결론 - 이 시스템은 화면에서 보이지 않는 백그라운드 작업이 크게 5종류다. 시장 데이터 수집/봉 생성, 시그널/리스크/주문, 체결/포지션 보정, 알림/UI fanout, 그리고 배치 기준정보 동기화가 서로 Kafka와 Redis를 통해 연결된다. 특히 포지션이 있는데 전략 보유 현황이 비는 문제는 체결 이벤트가 어떤 order_request.strategy_id와 매칭되어 strategy_position까지 replay 되었는지 확인해야 한다.

전체 흐름도 운영 포인트 API 백그라운드 Consumer 시장 데이터 Consumer 주문/포지션 Consumer 운영/알림 Batch 점검 체크리스트

운영자가 알아야 할 포인트

포지션/전략 보유 현황

권위 흐름은 KIS 체결 → order_execution → position → strategy_position이다. 전략 보유 현황은 주문의 strategyId가 살아 있어야 한다. 외부 주문이나 preinsert/backfill sentinel은 전략 보유로 자동 귀속되지 않을 수 있다.

화면과 실제 프로세스 분리

STOMP/API는 대부분 화면 업데이트용이다. 실제 주문/체결/손절/백필은 consumer와 batch가 수행한다. 화면에 안 보여도 Kafka 리스너와 scheduler는 계속 동작한다.

재연결은 단순 reconnect가 아니다

KIS WS 연결 성공 시 기존 종목 재구독, 체결통보 구독, onReconnect hook, REST 체결 backfill이 같이 움직인다. 재연결 로그가 많으면 KIS 호출도 늘어날 수 있다.

outbox는 조용히 쌓일 수 있다

Kafka/Slack 실패는 즉시 사용자 화면에 안 보일 수 있고, order_event_outbox, notification_outbox에 남아 retry worker가 뒤에서 처리한다.
