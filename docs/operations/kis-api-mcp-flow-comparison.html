v3.13.1 주문 hot path KIS 호출 0 H0UNCNT0 기본 ON MCP/API 채용 기준

KIS API/MCP 현행 → 변경 플로우 비교

이 문서는 v3.13.1에서 바뀐 KIS API 채용 방향을 주문 안정성 관점으로 비교한다. 핵심은 주문 직전에 KIS 잔액/가능수량 API를 추가 호출하지 않고, refresh 경로에서 만든 Redis snapshot만 읽는 것이다.

원본 문서: kis-api-mcp-adoption-plan.md · kis-api-reference.md

1. 결론 요약

주문 경로

변경 후에도 KIS REST 호출 0. 주문 라우터는 Redis snapshot만 읽고, 없거나 오래됐으면 pass-through 한다.

갱신 경로

inquire-balance 1회로 cash와 종목별 ord_psbl_qty를 같이 읽고 LWW snapshot으로 저장한다.

운영 채택

availability guard/refresh/insufficient reject는 기본 OFF이고, H0UNCNT0 통합 체결가는 기본 ON이다.

가장 중요한 보장: 여러 전략이 동시에 주문 신호를 만들어도 주문 앞에서 잔액조회 API가 전략 수만큼 폭주하지 않는다. 주문은 기존처럼 KIS 본주문 ACK/reject와 체결통보/reconcile을 최종 진실로 둔다.

2. 현행 주문 플로우

flowchart TD
    S["SignalGeneratedKafkaListener"] --> B["KIS balance fresh 조회<br/>currentCapital 산정"]
    B --> R["RiskGateway<br/>position/daily loss/frequency"]
    R --> I["order.intent.v1"]
    I --> O["OrderRouterKafkaListener"]
    O --> G["TradingModeGate<br/>KillSwitch<br/>MarketHours<br/>Canary"]
    G --> P["order_request REQUESTED 저장"]
    P --> K["KIS order-cash<br/>TTTC0012U/TTTC0011U"]
    K --> A["ACK"]
    K --> X["KIS reject"]
    A --> W["H0STCNI0/H0STCNI9<br/>체결통보"]
    W --> F["order_execution 저장<br/>position update"]
    F --> E["account.balance.changed.v1"]
    X --> E
현재 지점현재 동작문제 가능성
시그널 수량 산정 inquire-balance fresh 조회로 capital 산정 전략 burst 시 조회 호출이 늘 수 있다.
주문 라우터 본주문 order-cash만 호출 주문 직전 가능수량은 KIS reject가 최종 방어선이다.
체결 이후 WS 체결통보 + backfill/reconcile 체결 이벤트가 늦으면 UI/캐시 반영도 늦다.

3. 변경 후 refresh 플로우

flowchart TD
    Periodic["5분 periodic<br/>refresh-enabled=true일 때만"] --> Q["refresh queue<br/>key=userId+mode"]
    Event["account.balance.changed.v1<br/>FILLED/CANCELLED/REJECTED"] --> Q
    Q --> D["debounce 2s<br/>동일 userId+mode coalesce"]
    D --> L["KIS rate limiter<br/>BACKFILL priority"]
    L --> K["inquire-balance<br/>TTTC8434R/VTTC8434R"]
    K --> O1["output1<br/>hldg_qty + ord_psbl_qty"]
    K --> O2["output2<br/>dnca_tot_amt<br/>nxdy_excc_amt<br/>prvs_rcdl_excc_amt"]
    O1 --> S["AccountAvailabilitySnapshot"]
    O2 --> S
    S --> R["Redis putIfNewer<br/>versionMillis LWW"]
    R --> Key["account:availability:{mode}:{userId}<br/>TTL 15m"]
    L -. "429/EGW" .-> Retry["retry 2회<br/>delay 500ms"]
    Retry -. "소진" .-> Skip["snapshot 미갱신<br/>주문 path 영향 없음"]
항목현행변경 후효과
BUY 가능 금액 본주문 reject 또는 reconcile 후 명확 계좌 공용 cash snapshot 종목별 BUY 조회를 만들지 않는다.
SELL 가능 수량 position/reconcile에 의존 ord_psbl_qty를 종목별 map으로 저장 매도 가능수량 stale 위험을 줄인다.
호출 우선순위 주문/조회 경로가 섞일 수 있음 BACKFILL priority 본주문 USER_PATH와 경쟁하지 않는다.
rate-limit 실패 호출부에 영향 가능 snapshot 미갱신으로 종료 주문 path를 막지 않는다.

5. rate-limit 영향

flowchart LR
    User["USER_PATH<br/>order-cash/hashkey/주문 직결"] --> Priority["최우선"]
    Refresh["availability refresh"] --> Backfill["BACKFILL priority"]
    Backfill --> Coalesce["userId+mode coalesce"]
    Coalesce --> Periodic["5분 주기"]
    Coalesce --> Event["체결/취소/거절 이벤트"]
    Backfill -. "429/EGW" .-> Retry["500ms x 2"]
    Retry -. "실패" .-> Skip["snapshot 미갱신"]
왜 5분인가: snapshot은 주문을 막기 위한 실시간 API가 아니라 stale 위험을 낮추는 보조 권위다. 체결/취소/거절 이벤트가 갱신을 당기고, 5분 periodic은 이벤트 유실 시 안전망으로만 둔다.

6. KIS API/MCP 채용 변화

후보현재변경 후운영 코멘트
inquire-balance availability 잔고/position reconcile 중심 cash + ord_psbl_qty snapshot 주문 path 호출 0, refresh 기본 OFF
inquire-investor 미사용 외국인/기관/개인 수급 read-only adapter 상세/스크리너 보강용
inquire-ccnl WS 중심 최근 체결 REST read-only adapter WS stale 보강용
inquire-balance-rlz-pl 내부 journal 손익 중심 KIS REAL 실현손익 read-only adapter 모의 TR_ID는 공식 예제 부재라 REAL만
H0UNCNT0 H0STCNT0 + H0NXCNT0 기본 ON 단일 통합 체결가 이중 채널은 비상 롤백 경로
