캔들 데이터 저장 용량 점검

현재 magicJar DB의 candle 테이블 규모를 기준으로, 모든 종목 캔들 보유 전략이 어느 정도 부하를 만들지 계산한 운영 판단용 요약입니다.

849MB

약 130GiB
3,600종목 단순 환산

결론

모든 종목을 동일한 깊이로 1분봉부터 12시간봉까지 물리 저장하면 시스템 부담이 큽니다. 현재 23종목만으로도 candle 인덱스가 561MB라, 전체 종목으로 확장하면 Postgres가 캔들 저장소에 가까워집니다.

권장 방향은 전체 종목은 일봉 중심, 분봉은 관심종목·보유종목·전략 대상·거래대금 상위 종목만 보유하는 계층형 정책입니다.

용량 추정

시나리오 대상 예상 규모 판단
현재 방식 유지 23종목 849MB 이미 큼
핫 종목만 확장 100종목 약 3.6GiB 가능
전략 universe 확장 300종목 약 10.8GiB 관리 필요
전체 종목 동일 보존 3,600종목 약 130GiB 비권장
전체 종목 daily 중심 3,600종목 대략 4~6GiB 현실적

추정치는 현재 row당 저장/인덱스 비용과 보존 기간을 단순 환산한 값입니다. 실제 값은 종목별 상장 기간, 거래 시간, 보존 interval에 따라 달라집니다.

추천 보존 정책

전체 종목
종목 마스터, 상태 이력, 일봉, 주봉, 월봉 위주로 보유합니다. 시장 전체 탐색과 백테스트 후보 선별에 충분합니다.
기본 보존
관심·보유 종목
1m과 전략이 쓰는 interval을 보유합니다. 주문·리스크 판단에 직접 쓰이는 종목이므로 우선순위가 가장 높습니다.
핫 보존
전략 대상 universe
최대 100~300종목 정도로 제한합니다. 거래대금, 변동성, 관심등록, 최근 신호 발생 여부로 자동 편입/제외하는 방식이 적합합니다.
제한 필요
파생 interval
3m·5m·15m·30m·1h 등은 전 종목 물리 저장을 피합니다. 필요 시 1m에서 계산하거나, 실제 전략 interval만 저장합니다.
선별 저장
오래된 1m
Postgres에 계속 두지 말고 parquet/csv 같은 cold archive로 빼는 것이 좋습니다. 실시간 운영 DB는 최근 데이터 중심으로 유지합니다.
아카이브

바로 할 수 있는 정리

candle에는 중복 성격의 인덱스가 있습니다.

idx_candle_code_interval_ts와 idx_candle_code_interval_ts_v8가 같은 형태라 하나를 정리하면 현재 기준 약 167MB를 줄일 수 있습니다.

운영 전 개선

캔들 조회는 전체 fetch 후 필터링보다 WHERE code=? AND interval=? ORDER BY ts DESC LIMIT 500 형태가 안전합니다.

이 개선은 자동매매보다 먼저 넣는 편이 좋습니다. 종목 수가 늘 때 CPU와 DB I/O가 같이 흔들리는 지점을 줄입니다.
