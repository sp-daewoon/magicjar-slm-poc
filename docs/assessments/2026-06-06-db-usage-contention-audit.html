magicJar DB 사용·경합부 전수 감사

발행일 2026-06-06 · 측정 대상 magicjar-postgres (postgres:16-alpine, Up 5 days) · Flyway V68 · 테이블 55개 · 코드 전수 탐색(Explore) + pg_stat 실측 병행

핵심 결론 — 자동매매 용량의 1%도 쓰지 않은 현재, DB 973MB 중 87%가 candle이고 그중 561MB(66%)가 인덱스이며, 인덱스의 60%가 중복/사장 상태. 실매매 확장 시 경합은 주문 테이블이 아니라 candle의 쓰기 증폭(중복 인덱스 × upsert 재적재 × row-by-row insert)에서 먼저 온다. 자본 경로(order/outbox)는 멱등·락 설계가 이미 견고하다.

§6. 경합부(Contention) 분석 — 우선순위별

P1 candle 중복 인덱스 — 즉시 회수 가능한 167MB + 쓰기 증폭 주범

uq_candle_code_interval_ts      (code, interval, ts)       167MB — 23,219,649 scans (주력)
idx_candle_code_interval_ts     (code, interval, ts DESC)  167MB — 0 scans ← 완전 사장
idx_candle_code_interval_ts_v8  (code, interval, ts DESC)  167MB — idx와 정의 100% 동일 중복 (36,741 scans)
pk_candle                       (id)                         61MB
  • idx_candle_code_interval_ts와 idx_candle_code_interval_ts_v8은 정의가 글자까지 동일한 중복 인덱스. btree는 양방향 스캔이 가능해 UNIQUE 인덱스가 DESC 조회까지 커버한다.
  • 현재 모든 candle insert/update가 인덱스 4개를 동시 유지 — update 446만 × 4 = 쓰기 증폭의 주범이며, HOT update 3.3% 붕괴의 직접 원인 후보.
  • 조치: scan 0회 인덱스 제거 + v8↔uq 통합 검토 → 인덱스 ~334MB(전 DB의 1/3) 회수 + 장중 쓰기 부하 절반 수준 경감. Flyway V69 + DROP INDEX CONCURRENTLY.

P2 candle 스케일 폭발 — 실매매 유니버스 확장 시 1순위 경합점

  • 현재 1m 캔들 20종목 = 일 1.2만 행. 스크리너 유니버스 200종목 확장 시 1m만 일 12만 행, 13개 interval 합산 월 ~500만 행 — 수개월 내 candle 단독 수 GB.
  • 경합 구조: 장중 consumer WS boundary 쓰기(초 단위) + api 5분 incremental refresh upsert + frontend 차트 조회(idx_scan 2,300만)가 같은 hot page(최신 ts 구간)에 집중.
  • JPA batch insert 미적용(hibernate.jdbc.batch_size 설정 없음) — row-by-row INSERT라 커넥션 점유 시간이 종목 수에 선형 비례.
  • 조치: ① 분봉 retention 정책(예: 1m 6개월) ② fillfactor=90으로 HOT 회복 ③ batch_size 도입 ④ 장기적으로 ts 기준 파티셔닝 검토.

P4 자본 경로 — 현재 설계 양호, 스케일 시 주시점

  • ✅ order_event_outbox: FOR UPDATE SKIP LOCKED + 5초 drain — 다중 인스턴스 안전. 현재 FAILED 0건, 391건 전부 PUBLISHED.
  • ✅ order_request: Redis SETNX + DB UQ(idempotency_key) 이중 멱등 + HOT update 77% — row-level 경합 깨끗.
  • ⚠️ 장 시작 동시 시그널 폭주 시 outbox 5초 주기 × batch 100행이 직렬 병목 가능 — 단, 개인 계좌 1인 운영 규모에선 여유 충분.
  • ⚠️ NotificationOutboxRetryWorker는 SKIP LOCKED 없음 — 다중 인스턴스 배포 시 중복 발송 가능 (현재 단일 인스턴스라 비활성 리스크).

P5 커넥션 풀 — 현재 여유, candle 적재 직렬화가 잠재 변수

  • 합계 한도 20 (api 10 / batch 5 / consumer 5), 실측 idle 21 · active 1 — 포화 징후 없음.
  • 단, consumer 풀 5는 WS tick 적재 + outbox drain + Kafka listener + backfill이 공유 — 유니버스 확장으로 boundary 쓰기가 길어지면 outbox drain(자본 경로)이 풀 대기에 걸릴 수 있음. 스케일 시 consumer 풀 분리/증설이 첫 조치.
  • checkpoints_timed 1,209 vs req 1 — WAL 압박 없음. autovacuum 정상(candle dead tuple 0).
