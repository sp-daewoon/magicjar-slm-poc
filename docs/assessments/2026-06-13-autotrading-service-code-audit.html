2026-06-13 KST · 대상: api / consumer / batch / domain / strategy-engine / frontend / ADR·운영 문서

한 줄 결론 — 뼈대는 꽤 좋다. 신호→리스크→주문→체결→포지션의 경계가 살아 있고, KIS-first·MOCK/REAL 3중 게이트·ADR 0124 WS 재편도 상당 부분 코드화됐다. 다만 청산 SELL이 Risk Gateway에서 다시 막힐 수 있는 자본 경로 구멍과 Actuator/운영 UI 노출은 실계좌 canary 전 반드시 닫아야 한다.

§4. 핵심 발견

P0-canary blocker 자본 경로

1. 청산 SELL이 Risk Gateway에서 다시 막힐 수 있다

신호 생성기는 ADR 0114 방향대로 “BUY fail-closed, SELL 청산 진행”으로 분화되어 있다. 그런데 하위 RiskGatewayEvaluator에서 DAILY_LOSS_LIMIT, TRADE_FREQUENCY_MINUTE, TRADE_FREQUENCY_DAY가 BUY/SELL 구분 없이 적용된다. 손절·익절·DSL 청산 SELL이 일일손실한도나 분당/일별 빈도 한도 때문에 order.intent로 못 내려갈 수 있다.

근거

consumer/.../signal/RealtimeSignalGenerator.kt:200-204 — “fail-closed는 신규 자본 투입(BUY)에만, SELL은 막지 않는다” 불변식.

consumer/.../risk/RiskGatewayEvaluator.kt:67-112 — DAILY_LOSS_LIMIT가 side guard 없이 먼저 차단.

consumer/.../risk/RiskGatewayEvaluator.kt:170-198 — TRADE_FREQUENCY_MINUTE/DAY가 side guard 없이 차단.

consumer/.../risk/RiskGatewayEvaluator.kt:294-320 — preCheckFreeRules도 SELL 구분 없이 빈도 차단.

consumer/.../risk/RiskGatewayEvaluatorTest.kt:95-104 — SELL 통과 테스트는 MAX_CONCURRENT/POSITION_LIMIT만 검증. daily loss/frequency SELL 회귀 테스트 없음.

권장: DAILY_LOSS_LIMIT와 TRADE_FREQUENCY_*를 “신규 진입(BUY) 룰”로 명시하거나, ENTRY_TRADE_FREQUENCY와 EXIT_THROTTLE을 분리한다. 최소 회귀 테스트 3개를 추가한다: SELL+daily loss 도달, SELL+minute/day 한도 도달, preCheckFreeRules SELL 빈도 한도. 단, KILL_SWITCH_ON은 현재 테스트가 SELL 차단을 명시하므로 별도 ADR/결재 없이 풀지 않는다.

P1 운영·보안

2. Actuator/env/loggers가 인증 없이 통과된다

현재 코드는 단일 사용자 개발 환경에는 편하지만, VPS나 외부망에 열리는 순간 설정·환경·운영 제어면 노출이 된다. Spring Security도 없고, OnboardingGuardFilter가 /actuator/**를 통과시킨다.

api/.../OnboardingGuardFilter.kt:19-21 — Spring Security/JWT 미도입, user_account 존재 시 모든 API 통과.

api/.../OnboardingGuardFilter.kt:37-41 — /actuator/ 전면 통과.

api/src/main/resources/application.yml:65-72, consumer/.../application.yml:47-55, batch/.../application.yml:36-44 — health, info, metrics, prometheus, loggers, env 노출 + health details always.

docker/docker-compose.yml:99, :117, :170, :216, :251 — Dozzle/Kafka UI/api/batch/consumer host port 노출. Kafka UI는 AUTH_TYPE=DISABLED.

권장: REAL profile에서는 health,prometheus만 노출하고 env/loggers는 제거하거나 인증/IP allowlist 뒤로 보낸다. host binding은 127.0.0.1: 또는 VPN/internal network로 제한하고, health details는 never 또는 when-authorized로 바꾼다.

P2 성능·가용성

3. 주문 hot path가 KIS 체결 sync와 blocking I/O에 강하게 묶여 있다

주문 직전 KIS 당일 체결 sync는 데이터 정합을 높이는 좋은 안전장치다. 하지만 Kafka listener 한 흐름에서 모든 주문 전에 KIS REST sync가 수행되고, KIS 주문 어댑터도 .block() 기반이다. KIS 장애·rate limit·응답 지연이 order.intent 처리량과 p95 latency를 바로 흔들 수 있다.

consumer/.../order/OrderRouterKafkaListener.kt:147-151 — manualImmediate Kafka listener.

consumer/.../order/OrderRouterKafkaListener.kt:296-300 — 주문 처리 전에 sync guard 실패 시 reject.

consumer/.../order/OrderRouterKafkaListener.kt:676-705 — syncUserTodayExecutions를 매 주문 전 수행.

consumer/.../order/KisOrderHttpAdapter.kt:246-260 — KIS 주문 REST 호출 .block().

권장: “최근 N초 이내 complete sync” freshness cache를 두고 중복 sync를 줄인다. KIS sync latency, order.intent lag, KIS rate-limit wait를 S-1 dashboard에 붙인다. 장기적으로 WebClient blocking 호출을 격리 executor/boundedElastic 계약으로 표준화한다.

P2 모듈 구조

4. JPA scan 화이트리스트는 다시 누락될 수 있다

ADR 0103이 이미 같은 계열의 부팅 실패를 기록했는데, 현재도 api/consumer가 명시 package whitelist를 유지한다. 새 persistence root가 생기면 컴파일은 되더라도 런타임 부팅에서 repository bean 누락이 재발할 수 있다.

api/.../config/JpaScanConfiguration.kt:47-60 — api persistence, api.mcp.persistence, persistence.shared만 scan.

consumer/.../config/JpaScanConfiguration.kt:21-32 — consumer persistence, persistence.shared만 scan.

api/.../config/JpaScanConfiguration.kt:63-74 — 과거 mcp persistence 누락 hotfix와 장기 fix 후보가 주석으로 남아 있음.

권장: 최소한 api/consumer @SpringBootTest context smoke test를 “새 repository/entity 누락” 방지망으로 추가한다. 다음 사이클에서 ADR 0103 옵션 A(상위 패키지 scan) 또는 package convention enforcement를 정식화한다.

P2 정보보호·운영성

5. userId 로그 마스킹이 파일마다 다르다

일부 주문·계좌 파일은 maskUserId를 잘 쓰지만, risk/order/api 서비스 전반에는 raw userId={} 로그가 아직 많다. 개인 시스템에서는 낮은 위험이지만, 원격 로그/Slack/Dozzle로 퍼지는 순간 운영 데이터가 불필요하게 넓어진다.

consumer/.../risk/SignalGeneratedKafkaListener.kt:1068-1070 — SELL capital 조회 로그 raw userId.

consumer/.../order/OrderRouterKafkaListener.kt:689-699 — KIS sync guard 로그 raw userId.

consumer/.../order/TradingModeGateImpl.kt:74-104 — REAL gate 로그 raw userId.

docs/architecture/policies/logging-levels.md:36-66 — 로그 레벨 정책은 있으나 PII/masking 표준은 없음.

권장: 공용 UserIdLogMasker 또는 logging extension을 만들고, policy에 “userId는 기본 masking, audit table만 원문 보존” 원칙을 추가한다.

P2 확장성

6. KIS credential 조회가 multi-user 확장에 약하다

현재는 개인·single-tenant 전제라 큰 문제는 아니지만, 서비스 레벨로 보면 KIS credential을 accountType 전체 조회 후 userId로 필터링하는 코드가 반복된다. 사용자가 늘면 성능과 실수 여지가 생긴다.

consumer/.../order/KisOrderHttpAdapter.kt:106-110 — findAllByAccountType(...).firstOrNull { userId }.

consumer/.../order/KisOrderHttpAdapter.kt:372-377 — 취소 경로도 동일 패턴.

docs/architecture/policies/kis-credential-identity.md:16-25 — 식별 규약은 있지만 repository 직접 lookup 규약은 약함.

권장: repository에 findByUserIdAndAccountType를 1급 API로 두고, KIS auth/order/balance 계열에서 전체 조회 필터링을 제거한다. KIS WS execution notice도 single user 설정에서 multi-user 모델로 갈지 별도 결정을 남긴다.

§8. 결론

자동매매 본체는 “다시 처음부터 갈아엎어야 하는 상태”가 아니다. 오히려 지금은 구조가 꽤 성숙해져서, 남은 위험이 더 또렷하게 보이는 단계다. 가장 먼저 손볼 것은 큰 리팩터링이 아니라 SELL 청산을 절대 막지 않는 룰 경계와 운영 관리면 hardening이다.

이 두 가지를 닫으면 MOCK 운영은 계속 굴려도 되고, REAL canary도 “작은 금액 + 제한 종목 + 대시보드 관측” 전제로 한 단계 올라갈 수 있다. ADR 쪽은 구현보다 문서 전파가 뒤처진 상태라, 다음 설계 작업 전에 최신 SoT를 정리하는 편이 좋다.
