§2. producer key가 partition을 결정하는 방식

질문: 005930 ENTER와 EXIT가 둘 다 partition 7로 가게 하는 것은 누가 구현하나?

핵심은 producer가 Kafka record의 key를 같은 값으로 보내는 것이다. 우리 코드에도 이미 이 패턴이 있다.

// 현재 우리 코드와 같은 형태
// SymbolController.publishSymbolDetailCommand(...)
kafkaTemplate.send("symbol.detail.command.v1", code, payload)

// StrategyRealtimeDemandPublisher / ScreenerService / DaytradeDiscoverService 계열
kafkaTemplate.send("market.realtime.demand.v1", code, payload)

여기서 두 번째 인자 code가 Kafka key다. code="005930"이면 ENTER도 EXIT도 같은 key를 갖는다.

fun publishSymbolRealtimeCommand(code: String, action: String) {
    val payload = objectMapper.writeValueAsString(
        mapOf(
            "action" to action,      // "ENTER" or "EXIT"
            "code" to code,          // "005930"
            "userId" to currentUserId(),
        ),
    )

    // 중요: key = code
    kafkaTemplate.send("symbol.detail.command.v1", code, payload)

partition 7은 예시다. Kafka가 보장하는 것은 “같은 key는 같은 partition으로 간다”는 점이다. 실제 partition 번호가 7인지 3인지는 partition 개수와 hash 결과에 따라 달라진다.

개념적으로는 같은 “샤딩” 이야기지만, 구현은 다르다. Kafka 기본은 알파벳 범위 A~F가 아니라 hash bucket이다.

fun onDemand(record: ConsumerRecord<String, String>, ack: Acknowledgment) {

    val command = parse(record.value())

    when (command.action) {

        "EXIT"  -> router.release(command.owner, command.ownerId, code)

    ack.acknowledge()
}

패턴 C — Lease-Based Subscription Allocator

Kafka partition 소유와 별개로, Redis/DB lease가 “이 code+trId는 worker-2가 잡는다”를 결정한다. 동적 capacity와 worker 장애 복구가 쉬워진다.

data class Lease(
    val appKeyId: String,
    val trId: String,
    val code: String,
    val workerId: String,
    val version: Long,
    val leaseUntilMs: Long,
)

fun assignLease(command: DemandCommand): Lease {
    val worker = pickWorker(command.appKeyId, command.trId, command.code)
    val version = redis.incr("sub:assignment:version:${command.appKeyId}:${command.trId}:${command.code}")
    val lease = Lease(command.appKeyId, command.trId, command.code, worker.id, version, nowMs() + 30_000)

    redis.set(
        "sub:lease:${command.appKeyId}:${command.trId}:${command.code}",
        json(lease),
        ttl = Duration.ofSeconds(30),
    )
    kafkaTemplate.send("ws.worker.command.v1", worker.id, json(SubscribeCommand(lease)))
    return lease
}

§5. KIS appkey당 40 slot 파훼 패턴

먼저 인정할 것

KIS가 appkey/account 단위로 40을 제한한다면, 같은 appkey로 worker를 10개 띄워도 진짜 실시간 400개는 불가능하다. 가능한 것은 사용자/appkey별 quota를 분리하거나, 우선순위 기반으로 40개를 굴리는 것이다.

패턴 R1 — Priority Active Set

항상 필요한 것만 40개 안에 넣는다. 보유/미체결은 lock, 전략 후보와 상세 화면은 우선순위로 밀어낸다.

fun selectActiveWsSet(demands: List<Demand>, maxSlots: Int = 40): Selection {
    val reserved = 1 // H0STCNI execution notice
    val capacity = maxSlots - reserved

    val locked = demands.filter { it.owner in setOf(HOLDING, PENDING_BUY) }
    require(locked.size <= capacity) { "locked demands exceed KIS quota" }

    val candidates =
        demands
            .filterNot { it in locked }
            .sortedWith(compareByDescending<Demand> { it.priorityScore }.thenBy { it.lastSeenAt })

    val selected = locked + candidates.take(capacity - locked.size)
    val fallback = demands - selected.toSet()

    return Selection(ws = selected, polling = fallback)
}

패턴 R2 — Rolling Window / Squeeze Pattern

사용자 표현대로 “쥐어짜기” 패턴이다. 모든 400개를 동시에 WS로 보는 게 아니라, 낮은 우선순위 후보를 40개 단위로 회전시킨다. 단, 손절/청산 재료인 HOLDING은 절대 rolling 대상이 아니다.

slot 0~12HOLDING/PENDING_BUY 고정
slot 13~39STRATEGY/DETAIL 후보 27개
every 5~15s낮은 우선순위만 rotate
REST backfill미수신 구간 보완
fun rotateLowPriorityWindow(state: AppKeyState) {
    val locked = state.active.filter { it.owner in setOf(HOLDING, PENDING_BUY) }
    val rollingCapacity = 40 - 1 - locked.size

    val nextWindow =
        state.lowPriorityRing
            .next(rollingCapacity)
            .filterNot { it.code in locked.map { d -> d.code } }

    val target = locked + nextWindow

    val toUnsubscribe = state.currentWs - target.toSet()
    val toSubscribe = target.toSet() - state.currentWs

    ws.unsubscribe(toUnsubscribe)
    ws.subscribe(toSubscribe)

    // rolling으로 생긴 tick gap은 REST로 보완
    toUnsubscribe.forEach { gapFill.enqueue(it.code) }
}

한계: rolling은 “전 종목 실시간”이 아니다. 400개를 관찰하는 듯 보이게 만들 수는 있지만, tick-by-tick 정확도가 필요한 손절·미체결·시장가 근접 판단에는 쓰면 안 된다.

fun handleWorkerCommand(cmd: SubscribeCommand) {
    val current = assignmentStore.find(cmd.appKeyId, cmd.trId, cmd.code)

    // fencing token: 오래된 명령이면 무시
    if (current.version != cmd.version || current.workerId != workerId) {
        log.info("stale command ignored: code={} cmdVersion={} current={}", cmd.code, cmd.version, current.version)
        return
    }

    ws.subscribe(cmd.trId, cmd.code)
    assignmentStore.markActive(cmd.appKeyId, cmd.trId, cmd.code, cmd.version)
}

fun gracefulRevoke(assignment: Assignment) {
    assignmentStore.markDraining(assignment.key, assignment.version)
    ws.unsubscribe(assignment.trId, assignment.code)
    gapFill.enqueue(assignment.code, from = assignment.lastTickAt)
    assignmentStore.markReleased(assignment.key, assignment.version)
}

§7. Stateful Rebalancing: server 4 투입 시 정합성 답안

답: Kafka rebalance만으로는 부족하고, ownership handoff 프로토콜이 필요하다

서버 4를 새로 넣는 순간의 핵심은 “서버 1, 2, 3의 메모리를 서버 4로 복사한다”가 아니다. 실무적으로는 소유권, lease, checkpoint, Redis/API 갱신 권한을 버전 있게 넘긴다. 그래야 늦게 도착한 old worker 이벤트가 새 state를 덮어쓰지 못한다.

구분무엇이 이동하나안전장치우리 시스템 기준
Kafka partition rebalance consumer가 맡는 partition ownership offset commit, partition revoke/assign listener key=code이면 같은 종목 이벤트 순서가 partition 안에서 유지됨
Subscription assignment rebalance appKeyId + trId + code 구독 소유권 assignment version, lease TTL, fencing token KIS WS 구독은 이 계층이 진짜 핵심. 현재 로컬 map 구조만으로는 부족

현재 구조 판정: 문서의 target architecture에는 답이 있지만, 현재 코드 구조는 아직 완전한 답이 아니다. 이유는 demandsByCode, subscribedCodes, occupiedChannels가 worker 로컬 state라서 server 4가 들어왔을 때 전역적으로 “누가 무엇을 넘겨받는지”를 안전하게 합의할 저장소가 약하기 때문이다.

data class TickEvent(
    val appKeyId: String,
    val trId: String,
    val code: String,
    val assignmentVersion: Long,
    val eventTime: Instant,
    val price: BigDecimal,
    val sourceWorkerId: String,
)

fun onKisTick(event: TickEvent) {
    val current = assignmentStore.find(event.appKeyId, event.trId, event.code)

    // server-1이 늦게 보낸 tick이면 server-4 소유권을 덮지 못하게 차단
    if (current.version != event.assignmentVersion || current.workerId != event.sourceWorkerId) {
        log.info("stale tick ignored code={} eventVersion={} currentVersion={}",
            event.code, event.assignmentVersion, current.version)
        return
    }

    // Redis/API read model도 버전 조건부 갱신
    realtimeCache.upsertIfCurrent(
        key = "rt:${event.appKeyId}:${event.trId}:${event.code}",
        expectedVersion = event.assignmentVersion,
        eventTime = event.eventTime,
        price = event.price,
    )

    kafkaTemplate.send("market.tick.v2", event.code, event)
}

Kafka consumer rebalance listener에서 해야 하는 일

Kafka가 partition을 server 4로 옮겨주는 것은 “메시지를 누가 읽는가”의 문제다. 하지만 우리처럼 WS 구독과 Redis snapshot이 붙은 stateful worker는 partition 이동 순간에 local state를 flush하고, 새 partition에서는 assignment를 다시 읽어 재구독해야 한다.

class RealtimeConsumerRebalanceListener(
    private val assignmentStore: AssignmentStore,
    private val localState: LocalRealtimeState,
    private val wsBridge: KisWebSocketBridge,
) : ConsumerAwareRebalanceListener {

    override fun onPartitionsRevokedBeforeCommit(
        consumer: Consumer<*, *>,
        partitions: Collection<TopicPartition>,
    ) {
        // 1. 처리 중인 tick/checkpoint를 저장
        localState.flushCheckpoints(partitions)

        // 2. 이 worker가 더 이상 소유하지 않을 구독을 DRAINING 처리
        assignmentStore.markDrainingByPartitions(partitions)

        // 3. KIS unsubscribe는 version 확인 후 graceful 하게 수행
        wsBridge.unsubscribeRevoked(partitions)
    }

    override fun onPartitionsAssigned(
        consumer: Consumer<*, *>,
        partitions: Collection<TopicPartition>,
    ) {
        // 4. 새 partition에 해당하는 assignment를 전역 저장소에서 로드
        val assignments = assignmentStore.loadActiveByPartitions(partitions)

        // 5. fencing token 확인 후 resubscribe
        wsBridge.resubscribe(assignments)

        // 6. revoke/assign 사이 공백은 REST backfill로 보정
        localState.enqueueGapBackfill(assignments)
    }
}

현재 런타임 게이트의 의미

현재 방어는 “잘못된 데이터로 신규 매수하지 않게 막는 것”에 가깝다. 전략이 ACTIVE여도 candle readiness가 READY가 아니면 BUY 신호 발행을 억제한다.

// 현재 구조의 의미를 줄인 예시
val readiness = dataReadinessService.check(code, interval, boundaryTs)

if (!readiness.ready) {
    // 신규 자본 투입은 막는다.
    buySuppressed = true
    auditTrail.save("SIGNAL_SKIPPED_DATA_NOT_READY", readiness.reason)

    // 이미 보유한 자본 회수 경로는 살린다.
    sellAllowed = true
}

중요: 이건 “fail-closed” 보호다. 데이터가 이상하면 매수를 안 하는 것은 맞다. 하지만 사용자는 화면에서 전략이 ACTIVE라고 보는데 내부적으로는 계속 BUY가 skip될 수 있다. 그래서 서비스레벨에서는 READY/STALE/RECONCILING/NO_SLOT 상태가 명확히 보여야 한다.

왜 P1이라고 봤나?

여기서 P1은 “지금 당장 모든 거래가 터지는 P0”이라는 뜻은 아니다. 현재 BUY suppress가 있어서 잘못된 신규 매수는 어느 정도 막는다. 하지만 자동매매 서비스 관점에서는 전략이 ACTIVE인데 필요한 캔들이 준비되지 않아 신호가 조용히 skip되는 상태가 매우 위험하다.

§11. 결론

우리 시스템은 이미 api, consumer, batch로 나뉘어 있고 Kafka도 쓰고 있다. 하지만 KIS WS 구독은 아직 stateful local 구조다. 그래서 MSA 모양은 있지만, “consumer task 무한 증식으로 구독을 무한 처리”하는 분산 구독 시스템은 아니다.

대규모형으로 바꾸려면 단순히 task 개수를 늘리는 게 아니라, code key 기반 Kafka sharding, appkey별 quota scheduler, assignment/lease/fencing, worker rebalance protocol, global status UI를 한 세트로 설계해야 한다.

개발자 관점의 핵심 면접 문장: stateless service는 복제하면 확장되지만, stateful external connection은 소유권과 재분배 프로토콜이 곧 확장성이다.
