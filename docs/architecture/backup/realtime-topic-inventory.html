Realtime Topic Inventory

Runtime source 기준 Kafka topic, STOMP destination, KIS WebSocket tr_id를 한눈에 보기 위한 정리입니다. 이름만 봐도 transport와 owner가 드러나도록 다음 명명 규칙까지 함께 제안합니다.

41Kafka topics, including 4 DLT topics
17STOMP destination patterns
7KIS WebSocket tr_id / internal aliases
kafka stomp kisws api consumer batch shared cmd evt dlt

Naming Proposal

Kafka

kafka.{owner}.{kind}.{domain}.{resource}.{event}.v{version}

예: kafka.consumer.evt.market.tick.v1

STOMP

/topic/stomp.{owner}.{domain}.{stream}[.{key}]

예: /topic/stomp.api.market.tick.{code}

KIS WS

kisws.consumer.{domain}.{stream}.{variant}.{trId}

KIS 원본 tr_id는 유지하고 내부 표시명만 바꿉니다.

Why Rename?

Current Pain

  1. market.tick.v1만 보면 Kafka인지 STOMP인지 바로 안 보입니다.
  2. order.intent.v1처럼 API와 consumer가 함께 쓰는 토픽은 owner가 흐려집니다.
  3. STOMP는 /topic prefix만 있어 fanout이라는 정보는 있지만 API fanout인지 이름에 없습니다.
  4. KIS H0UNCNT0 같은 이름은 외부 명세라 의미를 사람이 계속 기억해야 합니다.

Rule

  1. Transport prefix: kafka, stomp, kisws.
  2. Owner prefix: api, consumer, batch, shared.
  3. Message kind: cmd, evt, dlt.
  4. Dynamic keys are last in STOMP, and stay out of Kafka topic names.

Migration Plan

  1. Registry-only PR: backend/TS constants로 raw string을 먼저 없앱니다.
  2. Kafka는 new topic 생성 후 producer dual-write, consumer dual-read로 한 도메인씩 이동합니다.
  3. STOMP는 API가 old/new destination을 병행 fanout하고 frontend가 new-first, old-fallback으로 이동합니다.
  4. KIS WS는 외부 tr_id를 바꾸지 않고 로그, metrics, slot ledger, runtime status label만 alias로 바꿉니다.
  5. 마지막에 old topic/destination을 retention window 이후 제거합니다.
