# magicJar SLM Lab — RAG 기반 도메인 Q&A 설계

- 작성일: 2026-06-18
- 상태: 설계 승인 대기 → (승인 시) 구현 계획으로 이행
- 범위: Phase 1 (RAG 전용, 훈련 없음)

## 1. 목표와 정체성

이 랩의 학습 목표는 다음 한 문장이다.

> **Opus/Fable 같은 대형 LLM이 magicJar 도메인에서 내놓는 좋은 답을 자산으로 삼아,
> 로컬 SLM(Gemma3:4b)이 LLM 없이도 magicJar 채팅 질문에 Opus만큼 답하게 만든다.**

- 형태: **채팅형 도메인 Q&A 챗봇** (에이전틱/코드수정 아님)
- 기법 본체: **지식 증류(distillation)**, RAG는 보조이자 데이터 공장
- 안전선: AI는 설명·초안만 생성. 매매/주문/전략활성화/실계좌 변경 권한 없음 (`CLAUDE.md` 준수)

### 세 메커니즘 구분 (혼동 방지)

| 기법 | 가중치 변경 | 역할 |
| --- | --- | --- |
| 프롬프팅 | ❌ | 즉시 지시 |
| RAG | ❌ | 추론 시점에 관련 문서/코드 조각 주입 (컨닝페이퍼) |
| 파인튜닝/증류 | ✅ | 도메인 감각·출력 형식을 가중치에 체화 |

최종 목표("LLM 없이도 잘함")의 본체는 파인튜닝/증류이며, RAG는 (1) 빠른 검증, (2) 증류용 학습데이터 생성을 동시에 담당한다.

## 2. 단계 로드맵

```
Phase 1 (현재)   RAG only. 훈련 0. "검색 → 주입 → 답"을 빠르게 작동 확인.
                 질문유형: 순수 지식 Q&A (DSL 문법 + 시스템 이해).
                 산출물: 작동하는 챗 + Opus 대비 채점 숫자.

Phase 2          RAG에 "코드 분석/설명" 질문 추가 (예: 저장 버튼 버그 짚기, 비에이전틱).
                 산출물: 코드 청크 검색 품질 + 분석 답변 채점.

Phase 3 (이후)   증류/파인튜닝. Phase 1·2에서 모은 (질문 → Opus답) 쌍으로
                 Gemma 가중치를 조정해 RAG 의존을 줄이면서 품질 유지.

Phase 4 (먼 미래) 도구를 쥐여주고 에이전틱으로 확장.
```

본 문서는 **Phase 1만** 정의한다. Phase 2~4는 별도 스펙.

### 핵심 원칙

1. 각 Phase는 반드시 **Opus와 비교한 숫자**로 끝난다 ("좋아진 것 같다" 금지).
2. RAG 산출물은 버리지 않고 **Phase 3 훈련 데이터로 재사용**한다.
3. 챗봇은 읽기전용 설명만. 안전선 유지.

## 3. RAG 아키텍처 (Phase 1)

RAG는 인덱싱(오프라인, 1회성)과 질의(실시간)로 시점이 나뉜다.

```
[인덱싱]  레포 파일(큐레이션) → 청킹 → BGE-M3 임베딩 → Qdrant 적재
[질의]    질문 → 임베딩 → Qdrant top-k 검색 → 프롬프트 조립 → Gemma3:4b 생성 → 답 + 출처
```

전 과정의 중간 산출물을 **반드시 화면에 노출**한다 (블랙박스 금지 — 사용자 1급 요구사항).

- ② 검색: 검색된 청크 원문 + 유사도 점수 + 파일 경로
- ③ 조립: 모델에 실제로 들어간 최종 프롬프트 전문
- ④ 생성: 토큰 수, 지연시간
- ⑤ 출처: 답이 참조한 파일 링크

### 기술 스택 (현업 표준 + 로컬/오프라인 가능한 것)

SaaS형 프로 툴(LangSmith, Pinecone, Arize 클라우드, OpenAI Evals)은 데이터 외부 전송이라 안전선 위배 → **로컬/오픈소스 구성원만 채택**한다.

| 레이어 | 채택 | 비고 |
| --- | --- | --- |
| RAG 프레임워크 | **LlamaIndex** | RAG 사실상 표준. 청킹/검색/조립 검증된 구현 |
| 벡터DB | **Qdrant** (도커, 포트 16333) | 현업 오픈소스 기본값, 도커 격리와 부합. 후일 pgvector 졸업 가능 |
| 임베딩 | **BGE-M3** (`bge-m3`) | 현업급 + 다국어(한국어 강함) |
| 생성 | **Gemma3:4b** (Ollama, 11434) | 기존 구성 재사용 |
| 관측("직접 보기") | **Arize Phoenix** (오픈소스, 포트 16006) | RAG 단계를 OTel 트레이스로 해부. 전부 로컬 |
| 평가 | **Ragas** + LLM-as-judge(Opus) | Ragas = RAG 평가 현업 표준 |
| 데모 챗 UI | **Streamlit** (포트 18501) | ML 현업 데모 표준 |

"직접 보기" 경로 둘:

- **Streamlit**: 질문 입력 + top-k 슬라이더 + 청크/프롬프트 펼침 + 답변 (체험용)
- **Phoenix**: 검색 청크·점수·프롬프트·지연을 스팬으로 해부 (현업식 RAG 디버깅)

### 인덱싱 대상 큐레이션

1,395개 Kotlin 전체를 넣으면 검색 노이즈로 품질이 망가지므로 **좁게 시작해 확장**한다.

- 포함: `docs/`, `memory/`, DSL 문법/파서 관련 코드, 핵심 아키텍처 Kotlin(전략리서치/빌더 흐름)
- 청킹: 코드는 함수/클래스 단위, 문서는 헤딩 단위
- **제외(안전): `build/`, `node_modules/`, `.env*`, 비밀키 포함 파일** → 비밀 유출 0

## 4. 평가 방법 — "Opus만큼인가"

```
질문 세트(magicJar 30문항)
  ├─ Gemma+RAG 답변  ─┐
  │                   ├─ Opus 심판: 정확성/완전성/근거 1~5점 + 우열 비교
  └─ Opus 답변(정답지)─┘
  └─ 기계 채점 병행: 출처 파일 정합성, (DSL 답이면) 파서 통과 여부
  └─ Ragas 지표: faithfulness, answer relevancy, context precision/recall
```

- **정답지 = Opus 답** (기존 `ClaudeCliStrategyResearchAiTextClient` 다리 재활용 → Phase 3 훈련데이터로도 재사용)
- 30문항 세트는 Phase 내내 **동일한 자(尺)**로 고정 — 튜닝/파인튜닝 전후 비교 기준
- 첫 30문항 초안은 magicJar 코드 기반으로 작성(구현 계획 단계에서 산출)

## 5. 배치·격리·안전

```
magicjar-slm-poc/
  slm-lab/                      # 새 Python 프로젝트 (Kotlin 본체와 분리)
    rag/
      indexing.py               # 큐레이션 → 청킹 → BGE-M3 → Qdrant
      query.py                  # LlamaIndex 검색 + Gemma 생성 (Phoenix 계측)
      app.py                    # Streamlit 데모 챗
    eval/
      questions.yaml            # 평가 30문항
      run_eval.py               # Ragas + Opus-judge 점수표
    pyproject.toml              # uv 기반
  docker/
    docker-compose.slm-rag.yml  # Qdrant + Phoenix (격리 포트, magicjar-slm-* 네이밍)
```

안전선 (`CLAUDE.md`/메모리 준수):

- 인덱싱은 읽기전용. 비밀/빌드 산출물 제외.
- 챗봇 시스템 프롬프트 가드: 설명·초안만, 주문/매매/전략활성화 출력 금지.
- 전부 로컬/오프라인. 외부 SaaS 전송 없음.
- 기존 magicJar 스택과 컨테이너/볼륨/포트/Kafka/Redis/DB 비공유.
